# Label propagation (FL-LABEL-PROPAGATION)

This flow follows a classification label from the person who declares it on a source column to the derived columns computed from that source. A source column's label is a decision. A derived column's label is a consequence of the columns it read, so nobody decides it. The flow also asks where a label is read once it is published. Two reference elements frame it:

- the security markings a data product carries, and a raised marking when data is combined ([DoD record](../alignment/dod-dmra.md), S12);
- authorization and access control ([NATO record](../alignment/nato-dcra.md), R6).

The labelling components are in [warehouse source](../components/warehouse-source.md) and [classification propagation](../components/classification-propagation.md). The access decision is in [need to know](need-to-know.md). Neither is repeated here.

**This record describes; it proposes nothing.** The remedies for its gaps are in [the roadmap note](../ROADMAP.md), each marked `proposed`. Statuses are those of [the README](../README.md). Line numbers are at the dag-tools pin listed there (`503607d`) for dag-tools, and at the invincible-agent pin for that repo. The record shape is provisional.

## Findings

1. **The owner labels the source per column.** A warehouse source's YAML carries one label per column, written as a set of values for each dimension. The hierarchical dimension is required, with exactly one value. An entry with no label at all is refused, so an empty entry cannot be mistaken for a column nobody labelled. Every label is checked against the mounted dimensions document, and a label that document does not declare fails the load. `built`
2. **An unlabelled column takes the strictest value in every dimension.** When the source is observed, each column the YAML does not label gets the most restrictive label the document allows: the top of the hierarchical dimension and the strictest value of every other dimension. The column is counted as defaulted and named in a warning. A label for a column the source no longer has fails the run instead, and so do two declared columns that differ only by case. `built`
3. **The source's label set is published twice.** The observation records it in the asset's metadata, one entry per column with its labels and glossary terms. With a catalog server set, the same set goes to the catalog as dataset properties and one glossary term per column per label value. A catalog failure fails the observation. `built`
4. **A derived column composes its label from the columns it read.** The propagation sensor reads the derived asset's column lineage and the published label set of each source the YAML declares. A column with lineage gets the least restrictive label that is still at least as restrictive as each of its source columns: the highest value on the hierarchical dimension, the union on a restrictive or exclusionary set, and the intersection on a permissive set. A source column with no published label fails the dataset rather than counting as unrestricted. `built`
5. **A column with no declared lineage takes the table's ceiling.** That ceiling, the table max, is the composition of every labelled column of every declared source, and the column's decision records the basis `table_max`. Composing no labels at all is refused. `built`
6. **Only a declared downgrade can widen a label, and it names an owner and a reason.** A rule carries an id, an owner, a reason and the label it sets, and the label is checked against the document at load. A rule is refused if it tightens any dimension, changes nothing, names a column the asset does not produce, or reaches a column another rule reaches. A dimension the rule leaves out keeps its derived value. Each application is recorded with the rule, the owner, the reason and both labels. `built`
7. **Propagation ships stopped.** The sensor's default status is `STOPPED`, and the schema accepts only `RUNNING` or `STOPPED`. Nothing is labelled downstream until a deployment starts the sensor. `built`
8. **Propagation is one step deep, and a chain fails closed.** The sensor reads a source's label set from the `columns` metadata of its newest observation or materialization, and expects each entry to carry `labels`. The sensor's own observation on a derived asset writes `columns` entries that carry `label`, together with the basis and the source columns. A derived dataset listed as another's source is therefore refused: "publishes column … without a label" when its newest event is that observation, and "publishes no label set" when it is a materialization. Either way the dataset fails and nothing is published for it. No test lists a derived dataset as a source. The schema itself refuses only a dataset that lists itself. AGENTS.md §4n states that chained propagation is not supported. `built`
9. **Published labels do not affect an access decision at either pin.** The gateway asks the policy engine for `can_read` on the dataset. In the invincible-agent policy at its pin, `can_read` is `reader | owner`, both relations on the dataset object, and no label is read. A search of the gateway, the broker and the client at the dag-tools pin finds no read of a label, a glossary term or a clearance rail. The rails that would carry a clearance are written down and empty ([need to know](need-to-know.md), finding 3). `built`
10. **Four texts at the dag-tools pin describe a broker that denies a dataset with no labels. That describes an intended rule, not the code.** The warehouse source example's README says that if the label set does not land, "a broker finds no labels on the dataset and denies every read of it". The same sentence is in the example's component file and in the warehouse source's `emit_payload` docstring, and the propagation component's `emit_propagation` docstring says a column whose terms do not land is "a column a broker finds unclassified". At `503607d` no broker or gateway code reads labels (finding 9), so a dataset whose labels never reached the catalog is decided exactly as one whose labels did. The rule those texts state is `proposed`, as [roadmap row 18](../ROADMAP.md). `built`
11. **No step of the flow is `measured` against a real catalog.** The composition, fallback, downgrade and stopped-default tests ran in process in the Tests workflow run cited in each component record. No test sends to a live catalog. `built`

## Gaps

- **Labels are not an input to the access decision** (finding 9). A label is published and composed, and no decision reads it. Remedy: [roadmap row 18](../ROADMAP.md). Status: `built`.
- **Four texts state a broker rule the code does not have** (finding 10). A reader of the warehouse source example would expect a dataset with no labels to be refused, and it is decided by relations alone. Remedy: roadmap row 18, for the rule; the texts are not on the roadmap. Status: `built`.
- **Propagation stops after one step** (finding 8). A dataset built from a derived dataset cannot be labelled by the sensor, and the refusal is untested. Remedy: [roadmap row 23](../ROADMAP.md). Status: `built`.

## Not established from code

- Whether a deployment has started the sensor. It ships stopped, and no chart template sets it running.
- Whether the policy engine's seed in a deployment loads the clearance rails. The rails are empty at the invincible-agent pin.
- What a live catalog does with the two patch aspects. No test sends to one.
