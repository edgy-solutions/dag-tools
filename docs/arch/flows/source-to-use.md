# Source to use (FL-SOURCE-TO-USE)

This flow follows data from a source table to a point of use. A pipeline copies the source into a root dataset. Later steps build derived datasets from that copy, and a consumer then reads one of them. The flow asks which record proves each link of that chain, and whether anything joins the records. Two reference elements frame it:

- the lineage and provenance a data product carries ([DoD record](../alignment/dod-dmra.md));
- the audit of who used which data ([NATO record](../alignment/nato-dcra.md)).

The access decision at the point of use is in [need to know](need-to-know.md), and the large read is in [big data](big-data.md). Neither is repeated here.

**This record describes; it proposes nothing.** The remedies for its gaps are in [the roadmap note](../ROADMAP.md), each marked `proposed`. Statuses are those of [the README](../README.md). Line numbers are at the component-records pin listed there (`add5bc4`) for dag-tools, and at the invincible-agent pin for that repo. The record shape is provisional.

## Findings

1. **The chain has three links, and each link has its own record.** (a) The source's own query history, matched to read tags, says which pipeline read which source object. (b) Lineage says what was built from what. (c) Read receipts at the gateway say who read which dataset, under which decision. The read audit produces the first, the asset graph and the catalog the second, and the gateway's ticket line and the client's receipt the third. `built`
2. **The tag covers only the first link, because only the first copy touches the source.** Every later step reads a copy, in a destination the pipeline wrote. So the source's history can show the first read and nothing after it. Every later link rests on lineage, and the last one on the gateway's receipt. `built`
3. **No shipped copier sets a tag.** The dlt pipeline, the contract mapping and the dbt project read with their own connections. A search of the package for a tag setter outside the audit engine and the tagged resource finds none. A copy made by any of the three is attributed only by time: the read audit credits an untagged read to an asset when it falls inside exactly one run window and that run selected one asset ([read audit](../components/read-audit.md), findings 6 and 7). Reads made through the tagged resource carry the tag. Its shipped users are the warehouse source, which observes a source, and the read audit, which reads query history; neither copies a source ([tagged warehouse](../components/tagged-warehouse.md#connections)). `built`
4. **A per-request read can bind the verified person instead of a pipeline.** `for_user` on the tagged resource puts a person's identifier in the tag in place of the pipeline principal. It changes the tag and not the credential, and the resource does not check the identifier: verifying it is the caller's job. No shipped caller uses it ([tagged warehouse](../components/tagged-warehouse.md), finding 4). `built`
5. **Lineage is recorded by five producers, each for its own step.** A dlt asset declares the source as a dependency and, when a source platform is known, names the source dataset's URN in its metadata. The lineage sensor reads that metadata and the asset graph's parents and sends lineage to the catalog. A contract mapping records the source dataset and the asset of record on its materialization. A dbt project's catalog recipe asks for column lineage. A warehouse source sends a lineage edge from the physical dataset to its asset. `built`
6. **The gateway's receipt says who read which dataset, and leaves out the narrowing the decision set.** Each issued ticket is logged as one line carrying the ticket id, the subject, the URN and the data's version. The subject is the one the broker was given. An issued ticket means the decision allowed the read. The columns and row filters that decision passed to the broker are not on the line. A denial from the explicit deny list is logged on its own line, and so is a policy engine's denial. The client can return a receipt beside the frame, built from an allowlist of ticket fields. `built`
7. **A read that does not pass the gateway leaves no receipt.** An agent engine's call to a dashboard tool goes to the tool directly ([Superset](../components/superset.md), finding 5). The engine sends the bearer token the chart supplies, which is empty by default. Nothing at either pin wires an API layer at all ([Hasura](../components/hasura.md), finding 1). Neither exit produces a gateway receipt, and the read audit does not see them. `built`
8. **No report joins the three records.** The read audit reads query history and run windows. It reads no lineage and no ticket log. The lineage sensor reads materializations and the asset graph. The ticket line goes to the gateway's log. No code at the pin reads any two of the three together. The read tag carries no ticket id ([roadmap row 17](../ROADMAP.md)), so a read made under a ticket cannot be matched to its source history by a shared key. `built`
9. **No link of the chain is `measured`.** Each producer has tests, and none of them runs a real warehouse, a real catalog or a real gateway log. `built`

## Gaps

- **No report joins source history, lineage and gateway receipts** (finding 8). Each link can be proved on its own, and the chain from a source read to a person's use cannot. Remedy: [roadmap row 20](../ROADMAP.md). Status: `built`.
- **Copies are attributed only by time** (finding 3). A copier's read of a source carries no tag, so it is credited only when its run selected one asset and no other run overlapped. Remedy: not on the roadmap. Status: `built`.
- **The receipt leaves out the decision's narrowing** (finding 6). A reader of the log can tell that a read was allowed, not which columns and rows it was allowed. Remedy: roadmap row 20 names the decision as an input to the joined report. Status: `built`.
- **Reads through a dashboard tool or an API layer leave no gateway receipt** (finding 7). Remedy: [roadmap rows 21, 22 and 24](../ROADMAP.md). Status: `built`.
- **The tag is unsigned, and a person's identifier in it is unchecked** (findings 2 and 4). Remedy: [roadmap rows 1 and 17](../ROADMAP.md). Status: `built`.

## Not established from code

- Whether a given warehouse's query history keeps a comment-placed or session tag, and for how long. That is the warehouse's behaviour.
- Whether any broker serves a warehouse source directly. If one did, a read under a ticket would touch the source object itself. The client sets no tag on a backend read ([roadmap row 17](../ROADMAP.md)), so that read would be untagged.
- Whether a dbt project's sources are the source tables themselves. Where they are, the dbt build is a first copy too, and it is untagged (finding 3).
- What a dashboard tool's own roles permit, and which database connections it holds. No code at either pin configures them.
- Where a deployment ships the gateway's log, and how long it is kept.
