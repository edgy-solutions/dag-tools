# Guide for AI Agents Operating on `dag-tools`

Welcome, AI Agent! When interacting with this project, you must adhere strictly to this operational guide to maintain safety, reusability, and consistency.

## Pre-Flight Checklist
Before modifying *any* code or executing external network commands, you **MUST**:
1. Read `README.md` to understand the library's purpose and how to test changes locally.
2. Read `llms.txt` to align your semantic context (this is a shared utility library, not a pipeline execution repo).
3. Read `.cursorrules` to ensure your proposed edits comply with the strict tech stack (`uv`) and type-hinting standards.
4. Before touching anything under `dag_tools/inventory/` or `dag_tools/qual/`, read [`docs/RECIPE.md`](docs/RECIPE.md) — it contains the load-bearing invariants and the ADRs explaining why the qualification system is shaped the way it is.

## Operational Safety Boundaries

### 1. Reusability Focus
- **DO NOT** hardcode project-specific logic, bucket names, or table names into this repository. 
- All resources, IO Managers, and sensors must accept configuration at runtime via Dagster's `ConfigurableResource` or `ConfigurableIOManager` patterns so downstream projects can inject their own values.

### 2. Declarative Component First (Dagster 1.12 GA)
- When building new data integration wrappers (e.g., DLT, DBT, Airbyte), use the **Dagster 1.12 GA Component API** (`dagster.components`). The old experimental `dagster-components` library is deprecated.
- New components **MUST** use the `Component, Resolvable, Model` triple-inheritance pattern:
  ```python
  class MyComponent(Component, Resolvable, Model):
      my_field: str
      def build_defs(self, context: ComponentLoadContext) -> Definitions: ...
  ```
- When integrating with event-driven or stateful engines like **Restate**, avoid loose programmatic Python factory scripts. Wrap the existing extractors inside Declarative Components (like `restate_dlt_sync` and `restate_api_sync`).
- Pipeline metadata, hints, and configurations should be offloaded to YAML structure rather than hardcoded Python factory kwargs.
- When defining `@asset` functions inside `build_defs()` with closure variables, use a **factory function** pattern — Dagster 1.12 introspects all function parameters as asset inputs.

### 3. Durable State Machines & Double-Writes
- When building handlers that modify both a database and an external API (e.g., `SapInductionService`), follow the **Double-Write / Outbox Pattern**.
- Every state transition (e.g., SUCCESS -> ERROR) must be recorded in the local database AND pushed to any remote callback/webhook APIs.
- Use Restate's `ctx.run()` to wrap **both** the notification and the update in separate, durable steps to ensure they are eventually consistent, even if one system fails.
- **NEVER** instantiate database clients or heavy resources inside a handler loop; use a global singleton/cache pattern to prevent connection leaks.

### 4. Restate Worker Deployment
- **DO NOT** write per-project Restate worker entrypoints or Dockerfiles. New durable handlers are registered in `dag_tools.restate_handlers.serve.SERVICE_REGISTRY` and ship in the shared `restate-worker` image (`Dockerfile.restate-worker`).
- Deployments select handlers and wire Restate **purely through environment variables** (`RESTATE_SERVICES`, `RESTATE_ADMIN_URL`, `RESTATE_ADVERTISED_URI`); the worker self-registers on startup. When adding a handler module, add its key to `SERVICE_REGISTRY` so it becomes selectable.
- **Never let a handler raise on every non-2xx HTTP response.** `ctx.run` retries whatever raises, so a status the plan is meant to *branch on* (a 404 that should trigger a fallback) would be retried with backoff forever and the branch would never execute. Return the status as data from the `ctx.run` closure and classify outside it: 2xx succeeds, a status with a declared fallback runs that fallback, retryable statuses (5xx / 429 / 408) raise so Restate retries, everything else raises `restate.TerminalError`. See `dag_tools/restate_handlers/api_call_plan.py`.
- **Keying a VirtualObject serializes; it does not deduplicate.** Two dispatches of the same key are two invocations, and `ctx.run` only dedupes retries *within* one. Any handler whose calls are append-shaped (recording an event, not upserting a row) must persist what it has already completed in object state and short-circuit a repeat — and the producer should carry a matching guard so the duplicate is never sent.
- **A private CA needs TWO env vars and a MERGED bundle — never one, never a substitution.** `restateWorker.caCerts` / `centralGateway.caCerts` exist because the handlers use both `requests` and `httpx`, and the two disagree: `requests` honours `REQUESTS_CA_BUNDLE` and ignores `SSL_CERT_FILE`, `httpx` the reverse. Setting one leaves half the call sites rejecting the endpoint — including the worker's own Restate registration, which is httpx, so the worker serves nothing and the symptom looks like a deployment fault rather than a certificate one. Both vars also *replace* the trust store rather than extending it, so naming the operator's cert directly breaks every public endpoint (measured: httpx to pypi.org is rejected) — which is why an init container concatenates the system roots, certifi's bundle and the mounted certs, and the env vars name that merged file. Do not "simplify" this to a single env var pointing at the mounted secret. Regressions: `test_chart_ca_certs.py` — `test_enabling_sets_both_env_vars`, `test_the_env_vars_name_the_MERGED_bundle_not_the_mounted_secret`, `test_the_merge_keeps_the_public_roots`, and the `TestWhatTheClientsActuallyHonour` canary that pins the library behaviour the design rests on.

### 4a. OTel -> API sync (`dag_tools.otel_api_sync` + `OtelApiSyncComponent`)
- The mapping engine is **pure**: no Dagster, Restate or dlt imports. The Dagster component, the Restate handler and the tests all share it. Keep it that way — it is what makes the mapping semantics testable without infrastructure.
- **Render Dagster-side, execute Restate-side.** Plans are fully rendered before dispatch so `dry_run` shows the exact bytes and mapping edits need no worker redeploy. The corollary is binding: the handler has **no template engine**, so every fallback body must be renderable before anyone knows which call failed.
- **A fallback must never be able to touch items that succeeded.** Bulk creation endpoints commonly have *replace* semantics, so a group-wide fallback silently destroys server-side state that was never in the telemetry. `mode: item` re-renders in the failing item's scope only; `mode: aggregate` pre-renders one `fragment` per call and the handler splices in only the fragments of calls that actually failed. Do not add a fallback mode that renders over the whole group.
- **Type fidelity is not optional.** Templates render through `NativeSandboxedEnvironment` (`SandboxedEnvironment` + `NativeEnvironment`), so a single-expression template returns a real `int`/`bool`/`list`. Sandboxing and native typing come from *different* Jinja classes — using `SandboxedEnvironment` alone quietly stringifies every numeric, boolean and array payload field. OTel attribute columns are `Map(String, String)`, so coercion helpers (`as_int`, `as_float`, `as_bool`, `split`, `metrics_from_prefix`, `to_iso`) are the norm, not the exception.
- **Numbers are exact or absent; never `NaN`, `Infinity` or a rounded integer.** JSON cannot carry non-finite numbers (httpx 0.28 serializes with `allow_nan=False`), and two silent paths used to produce them. First, Jinja's `native_concat` runs `ast.literal_eval` on every string result, so a plain `{{ attr(...) }}` over an identifier like `"8e01234"` rendered as `inf`; `_json_safe_native_concat` keeps the original string whenever the parse yields a non-finite float or a complex, and changes no other parse, because mappings rely on `"0"` arriving as `0`. `NativeTemplate.render` reads `concat` from its `environment_class`, so the override needs the matching `_NativeSandboxedTemplate`; overriding `concat` on the environment alone silently does nothing. Second, `as_int` / `as_number` went through `float()`, which rounded integers past 2**53; integer text now parses exactly, non-finite input returns the default, and `as_int` refuses a float-parsed value outside the exact range. `build_plan` then refuses any non-finite float that still reaches a plan (a raw column value), naming the field path, so dry runs fail the same way the send would. Regressions: `test_otel_api_sync_numeric.py` -- `test_a_string_whose_literal_parse_json_cannot_carry_stays_a_string`, `test_ordinary_literal_parsing_of_a_string_result_is_unchanged`, `test_integer_strings_parse_exactly_past_float_precision`, `test_a_raw_non_finite_value_fails_the_render_and_names_the_field`.
- **Gate on group readiness before dispatching.** Telemetry for one execution group arrives across multiple extraction runs; dispatching a half-filled group sends incomplete collections as authoritative upserts. Use `readiness.quiet_period_seconds` / `complete_when` / `max_age_seconds` rather than assuming a group arrives atomically.
- **Schedule from YAML with `cron_tick_passed(...).since_last_handled()`, never `on_cron`.** The component ships no schedule or sensor; operators attach a condition through `post_processing` (the example README's block) and Dagster's `default_automation_condition_sensor` picks it up, because that sensor is built from the final asset graph, after post-processing. Note that it is created **stopped**. `on_cron` cannot work here: it includes `all_deps_updated_since_cron`, and the extraction asset's upstream is the external ClickHouse source spec, which never materializes, so extraction is never requested and dispatch waits behind it forever, with no error. Python's `.ignore(AssetSelection...)` escape is unavailable in YAML (the `dg` template scope exposes no `AssetSelection`). Triggering is time-based because readiness is. Regressions: `test_otel_api_sync_automation.py` -- `test_readme_condition_requests_extraction_and_dispatch_on_every_tick` (reads the block out of the README), `test_on_cron_never_fires_for_this_component`, `test_yaml_automation_gets_the_default_sensor_which_starts_stopped`. **The YAML route needs a Dagster whose component file accepts `post_processing`, and 1.10.19 -- the compat floor, and the version production runs -- does not.** It rejects the file with `extra_forbidden`, which fails the whole component load rather than just the schedule, so there is no YAML schedule on that version at all and the condition has to be set from Python. The three tests above probe that by the raised error, not by a version number or an import path, and skip naming the missing field; anything else that goes wrong in the loader still fails loudly.
- Lookups are **normalization-tolerant** (`normalize_key`) because dlt snake-cases identifiers into the staging destination *and* flattens nested maps into `parent__child` columns. One mapping file must work in both staged and direct mode; do not add a code path that assumes either naming. Anything that scans attributes in bulk must resolve its bags via `attribute_bags()` — resolving the map column by exact name returns nothing after staging, and an empty result passes any `all(... for x in xs)` assertion vacuously.
- **Pin OTel attribute maps to JSON on the way into staging** (`DEFAULT_MAP_COLUMNS` in the ClickHouse source). dlt's flattening lower-cases every path part, so `metric.NUM_ERROR` is unrecoverable as `num_error` — casing cannot be restored downstream.
- **Percent-encode path substitutions** (the `finalize` hook on the path environment), never the literal separators. Note the hard limit: an identifier containing `/` cannot travel in a path segment at all, because servers decode before routing — route those through the query string or body instead. Both facts were found by running the example, not by review.
- **A failed plan is recorded, never raised.** `execute_plan` never lets a plan-level failure escape as `restate.TerminalError`: Dagster dispatches through `/send`, the one-way ingress, so nothing would ever observe a raised exception, and a terminal failure rolls back the very object state the failure record needs to survive in. A halted plan instead sets `status: "FAILED"` in state and returns normally; calls already delivered before the halt are still banked in `completed_call_keys`, but the plan hash is withheld from `completed_plan_hashes` so a corrected re-dispatch is let through. Regressions: `test_unhandled_client_error_halts_and_is_recorded_not_raised`, `test_halted_plan_banks_calls_delivered_before_the_halt`, `test_halted_plan_does_not_record_its_plan_hash_as_completed`, `test_halted_plan_does_not_execute_a_later_step`.
- **Non-secret API config belongs on the Dagster side, not the worker's environment.** `component.yaml`'s `api:` block (`base_url`, static `headers`, `timeout_seconds`) is resolved by Dagster's own `{{ env.X }}` substitution and merged over the mapping's `api:` block in `_load_mapping` *before* `load_spec` validates it — mapping.yaml stays portable and need declare no `base_url` at all. Setting `api.base_url` on the component MUST also pop `api.base_url_env` from the merged document, or `_resolve_api`'s existing precedence would let the worker-side env var keep silently winning. `api.plan_carried_headers` is the one path that renders a header value straight into the plan (and therefore into the Restate journal) — a deliberate, separately-named field so that decision is never an accident.
- **The completion check classifies on `last_result` before `completed_plan_hashes`.** `restate_plans_completed` polls each dispatched group's `get_status` and must check `last_result.plan_hash == plan_hash` first, since a `COMPLETED_WITH_ERRORS` plan *does* get its hash recorded in `completed_plan_hashes` — checking that list first would report a partially-failed plan as a pass. Regression: `test_completion_check_treats_completed_with_errors_as_a_failure`.
- **`dest_config` takes the same shape here as in every other component, and explicit parts beat the env var.** Both halves of this component resolve the staging destination through the one shared `config_to_credentials`: the dlt writer, and `_staging_engine` for the read-back. That read-back used to roll its own precedence, preferring `credentials` and then `DESTINATION__<DRIVER>__CREDENTIALS` and only falling through to `host`/`username`/`password` last — so a DSN env var left over from another pipeline silently retargeted the read away from the host the operator had named, and the parts shape everything else in the repo uses felt second-class. Order is now explicit config (parts or DSN), then the env var as last resort. Regressions: `test_explicit_dest_config_host_beats_the_ambient_dlt_env_var`, `test_staging_engine_accepts_the_same_host_parts_as_every_other_component`.
- **Staging-destination resolution is `_staging_url`; `_staging_engine` only wraps it.** `sa.create_engine` eagerly imports the DBAPI, and CI installs no postgres driver, so any test that built an engine died on `ModuleNotFoundError: No module named 'psycopg'` — green locally, red on every runner. Resolution is the part this module decides and the part worth pinning, so it returns a URL string that tests parse with `make_url`. Never assert on a live engine here.

### 4l. Classification: the dimensions file and the asset of record (ADR-0064 steps 3-5)
*The rules every reader of the dimensions file is built to. `warehouse_source` (4m) is the first of them; gov builds the ConfigMap to the name in the first bullet. Numbered 4l because `contract_mapping` took 4k.*
- **dag-tools ships no classification file; it reads the deployment's copy, at the same mount as before.** Ruled by Chris on 2026-11-05 and amended by him the same day: one file, owned by policy at `invincible-agent/policy/classification/`, served to dag-tools as a ConfigMap mount, so code reads what the server serves rather than a copy that can disagree with it. The amendment replaced the single ordered list of levels with a **set of dimensions**, one of them hierarchical. The mount is deliberately unchanged — env **`DAGTOOLS_CLASSIFICATION_LEVELS`**, default **`/etc/dagtools/classification/levels.yaml`** — because the amendment says "same path", and because the hierarchical dimension *is* the former levels list, so what gov rebuilds is the ConfigMap's content, not its wiring. That path is a *mount location*, not a name from below, which is why it may carry a default at all. Top-level key `classification_dimensions`; each dimension carries `id`, `hierarchical: true|false` and an ordered `values` list whose rows carry `id`, `reason` and `ratified_by` — the same per-row fields the levels document already had. (Renaming the env var and filename to match the new content is a one-line change here plus a chart change in gov; it is not assumed.)
- **Exactly one dimension is hierarchical, and the file says which — a count of zero or two FAILS the load.** The ceiling rule, "most restrictive" and the downstream `max` are each defined only on a ladder, so a document that declares no hierarchical dimension, or more than one, is ambiguous in a way no code should resolve by picking. Failing the load is also what keeps the next bullet honest: dag-tools learns which dimension is the ladder from the `hierarchical` flag, never from a name it carries itself.
- **Order is list position within a dimension, least restrictive first, and a clearance is a CEILING on the hierarchical dimension only.** A group cleared at a hierarchical value reads that value and every earlier row — never an exact match, which would deny a cleared reader everything below their own level. On any other dimension there is no ladder, so a clearance is membership — and **amended 2026-11-06 to align with OpenDDIL ADR-0055, how that membership is checked is itself declared**, one of three kinds: a **permissive set** (the reader holds ≥1 of the column's values), a **restrictive set** (the reader holds all of them) and an **exclusionary** one (the reader holds none of them). Access is the conjunction across dimensions. The earlier reading — every unordered dimension conjunctive — is exactly the restrictive set, which is why an undeclared `type:` still means that and a document already mounted means today what it meant yesterday. The rail is `holds:<dimension>:<value>` for a set dimension and `cleared_for:<level>` for the ladder; that spelling is policy's call and is flagged to gov rather than invented here. `can_read` is unchanged. The policy rail lists each group once at its highest hierarchical value. The Topaz relation was `cleared_for:<level>` and now has to carry the dimension too; that spelling is policy's call and is flagged to gov rather than invented here. `can_read` is unchanged.
- **An absent or empty file means every column is MOST restrictive in EVERY dimension — in practice, nothing is served.** Not "unclassified, therefore readable". With dimensions, most restrictive means the last row of the hierarchical ladder, every value of every restrictive and exclusionary dimension — and, since the 2026-11-06 amendment, **no** value of a permissive one, because a reader needs one of a permissive set and so the empty set releases to nobody. Empty is the floor on a permissive dimension and the ceiling on every other, which is the one place the four kinds do not line up; and when the file is absent there are no declared values to validate against at all, so no read can be authorized. That is the intended failure mode: a missing mount is indistinguishable from a mount that failed, and the permissive reading ends with a governed column served to someone with no clearance. The file also legitimately ships with nothing ratified yet, so an empty dimension list must not be read as "nothing is restricted" either.
- **No dimension id and no value string appears anywhere in dag-tools — not as a constant, not as a default, not in a comment.** The amendment widens the old no-level-strings rule by one notch: the *name* of the hierarchical dimension is as much a governance decision as the values on it, so it is discovered from the document's `hierarchical` flag. A component taking a label validates every dimension id and every value against the mounted file and fails the load on anything the file does not declare. Same reasoning as 4j and `dag_tools.audit`: a level — or now a dimension — compiled into the library turns a governance-board decision into a library release.
- **A `warehouse_source` column label is `{dimension: values}` with the hierarchical dimension REQUIRED.** Amended 2026-11-05; it replaces the `level` scalar in the step 4a spec, which is now `columns: [{name, labels: {<dimension id>: <value> | [<values>]}, cell_predicate?}]`. The hierarchical dimension takes exactly one value — a list there is ambiguous (a range? a maximum?) and is refused rather than interpreted. A column with **no entry at all** is most restrictive in every dimension, as above; a column that *has* an entry but omits the hierarchical dimension is an operator mistake, not a default, and fails the load — the two cases are distinguishable and must stay so, because silently defaulting a half-written label is how a column gets labelled by accident.
- **Downstream propagation (4b/4c) composes in each dimension's own algebra, and it is NOT a union everywhere.** One rule — no output column is less restricted than the source columns it is computed from — read through each declared kind: `max` on the hierarchical one, **UNION** on a restrictive or exclusionary set, and **INTERSECTION** on a permissive one. The permissive case is the 2026-11-06 amendment's, and it is the opposite of the three others because a wider permissive set admits *more* readers: unioning two sources there would publish a derived column as readable by people who could read neither of them. All four are the least upper bound of one order — "does this admit at least every reader that does?" — which is why the composition is one function per dimension rather than four rules (§4m). Column lineage is still the input (dbt column lineage; `TableColumnLineage` required on a Python asset reading a labelled source; absent → table max, which with dimensions means the per-dimension composition over the whole table). A downgrade is declared `{dimension, value, reason, steward}` — it now names the dimension, since downgrading one says nothing about the others — and **no downgrade is automatic**: a standing one is a declared rule with a named owner, and each application is recorded with the rule, the owner, both labels and the reason. Seals fail on an unlabelled input, a downgrade without a reason, a standing rule with no named owner, an unrecorded application, and a value outside its dimension's vocabulary.
- **The asset of record is the PHYSICAL platform's dataset URN, never a `dagster` platform URN.** Ruled 2026-11-05: `s3` for a file-backed fixture, the warehouse's own platform for a warehouse source. The catalog sync registers the dataset under the physical platform and attaches the Dagster asset as **lineage** — so a broker authorizing a read and a catalog describing it name the same object. Anything built on these URNs (`warehouse_source`, the contract mapping's `dataset_urn`) is built to the physical form.

### 4m. Warehouse source (`dag_tools.warehouse_source` + `WarehouseSourceComponent`)
*Steps 4a-4c of ADR-0064 and the first reader of the dimensions file 4l names. One component instance = one labelled source dataset, observed rather than moved; `propagate.py` is the engine 4b/4c composes derived labels with. Numbered 4m because `contract_mapping` took 4k and the classification rules took 4l.*
- **The asset of record is the physical dataset URN, and a `dagster` platform URN is REFUSED at the load rather than discouraged.** 4l's ruling, enforced where it can still be obeyed. The failure it prevents is invisible once shipped: the catalog would describe one object, a crawler would discover a second, and a broker asked to authorize a read of the physical one would find no labels on it. The Dagster asset attaches as **lineage** — an `UpstreamLineageClass` whose downstream node is the `dagster` platform dataset for the asset key, with the physical dataset upstream — and the fabric of that node is read off the operator's own URN (`env_of`), never named here, because a lineage node in the wrong fabric is a second object again. Regressions: `test_a_dagster_platform_urn_fails_the_load`, `test_the_asset_of_record_may_not_be_a_dagster_urn`, `test_the_physical_dataset_is_the_entity_every_label_is_attached_to`, `test_the_lineage_edge_runs_FROM_the_physical_dataset_TO_the_asset`, `test_the_asset_key_in_the_lineage_node_is_the_prefixed_key`.
- **The dimensions document is read at MATERIALIZATION, and an absent document fails the run — not the load.** Both halves are deliberate. Re-reading at observation time is because the mounted document is the authority at the moment of the read: a label validated at deploy time says nothing about what the board has changed since, and the published label set records which document and which digest ratified it. Failing the *run* rather than the load is because one unmounted ConfigMap would otherwise take every other asset in the code location down with it — a strictly worse failure than a source that refuses to publish — and deny-by-default is not weakened by it, since publishing only happens in the run. A label the document *contradicts* is a different case and does fail the load: it needs no mount at run time to already be wrong. Regressions: `test_an_absent_document_loads_and_then_fails_the_run_naming_the_path`, `test_a_label_the_document_does_not_declare_fails_the_LOAD`, `test_the_published_label_set_says_which_document_ratified_it`.
- **`fetch_columns` is a SEPARATE seam from `fetch_rows`, and an empty table is the reason.** Measured against real sqlite rather than reasoned about: a projection matching no rows yields no rows at all, so column names taken off the first row report a source with **zero columns**. Deny-by-default would then publish a table with nothing on it, and every label the operator declared would fail as stale — a correct, labelled, empty source would look like a renamed one. `column_names_from_result` reads the result's own keys and falls back to the cursor description. A schema read is still a read, so it is refused at the same chokepoint if it cannot carry its tag. Regressions (in `test_tagged_warehouse_resource.py`): `test_an_empty_result_set_still_names_its_columns`, `test_a_result_that_refuses_keys_falls_back_to_the_cursor_description`, `test_fetch_columns_is_a_separate_seam_from_fetch_rows`, `test_a_schema_read_still_has_to_carry_its_tag`.
- **An observable source asset takes NO run config — measured on both versions, not assumed.** Dagster calls the function as `observe_fn(context, **resource_kwargs)` (`_core/definitions/source_asset.py`), so a pythonic `config:` parameter raises `TypeError: ... missing 1 required positional argument: 'config'` at **run** time, not at definition time, identically on 1.10.19 and 1.13.1 — a knob that would look wired up until the first materialization. `observable_source_asset` likewise has no `owners` parameter, so the owner travels as metadata and to the catalog. Every knob therefore arrives as a YAML attribute, which is where this library wants them anyway. Regression: `test_the_observe_function_takes_no_run_config`.
- **`AssetSelection.all()` does NOT include source assets: a job built that way runs zero steps and reports `success: True`.** Found by running the example. Any test, job or schedule that observes this asset must name the keys (`AssetSelection.assets(*keys)`) — a harness written against `all()` passes while observing nothing, which is the vacuous-pass shape this repo keeps finding. The example README says it too, because an operator attaching automation hits the identical trap.
- **A catalog failure FAILS the materialization — deliberately the opposite of §4i.** The dbt publisher swallows every DataHub error because that build's value is the tables it produced and an outage must not cost them. Here the publish *is* the deliverable: a source whose labels never reached the catalog is one a broker will be asked about and answer unlabelled, which under deny-by-default serves nothing and presents as an outage somewhere else entirely. `dry_run` is how an operator sees the payload without a server. As in §4i, **no** `token` key is emitted when there is none — `""` is sent as a credential and rejected. Regressions: `test_a_catalog_failure_FAILS_the_materialization`, `test_an_empty_token_is_never_sent_as_a_credential`, `test_dry_run_records_everything_and_emits_nothing`.
- **No `schemaMetadata` aspect is emitted, because only column NAMES were read.** The observation reads no types, and an aspect asserting a shape nothing looked at is a fabrication a crawler would then disagree with — `schemaMetadata` is the crawler's aspect. The labels ride on `EditableSchemaMetadata` glossary terms per field, which is also where a human edit lands. Regressions: `test_no_schema_aspect_is_emitted_because_only_names_were_read`, `test_every_term_on_a_column_reaches_the_field_it_labels`.
- **`require_ratified` gates on `values_without_ratification`, NOT on `unratified`.** Two different questions with nearly the same name, and the near-fit shipped as dead code until the engine was read rather than trusted: `unratified` reports a *dimension* that declares no values at all — the complement of `is_usable` — so the gate could never fire and its message named the wrong thing. A declared value with nobody's name against it is a legitimate state (the document stands up before the board has signed every row), so it is reported as `unratified_values` in the observation metadata and refused only where a deployment opts in.
- **An unlabelled column is most restrictive in every dimension and is COUNTED; a labelled column the source no longer has RAISES.** The two cases must stay distinguishable. A missing label is a gap the metadata reports (`defaulted_columns`, plus a warning) and deny-by-default makes it under-serve rather than over-serve. A stale label means the YAML describes a different table than the one observed — publishing it would govern a name that no longer exists while serving the renamed column to nobody — so it fails loudly instead. Matching is case-insensitive with the *source's* spelling published, and a fold collision is refused rather than resolved. Regressions: `test_an_unlabelled_column_is_published_most_restrictive`, `test_a_labelled_column_the_source_no_longer_has_fails_loudly`, `test_the_declared_spelling_is_only_how_the_column_was_found`, `test_columns_differing_only_by_case_are_refused`.
- **Composition is one partial order read four ways, not four rules.** `Dimension.at_most_as_restrictive_as` asks the same question of every kind — does this label admit at least every reader that one admits? — and `most_restrictive_of` is its least upper bound, which works out as `max` on the ladder, union on a restrictive or exclusionary set and intersection on a permissive one (§4l). Writing it as four independent branches is how one of them ends up pointing the wrong way, and the one that would is the permissive set, where every intuition from the other three is backwards. `most_restrictive()` and `least_restrictive()` come off the same order, so deny-by-default needs no branch at its call sites. Regressions: `test_warehouse_source_propagation.py` — `test_composition_is_the_join_of_one_order_in_every_type` (parametrised over all four), `test_a_permissive_set_composes_by_INTERSECTION_not_union`, `test_the_most_restrictive_permissive_set_is_empty_and_releases_to_nobody`, `test_an_untyped_dimension_still_means_what_it_always_meant`.
- **A DERIVED label is total; a DECLARED one is partial. Never compare them directly.** `Label.values_for` answers `()` both for a dimension a label leaves out and for one it carries empty, and on a permissive set those mean "no restriction" and "nobody" — opposite answers. So a derived label always carries every dimension (`Label.declares` is the only honest membership test), and a declared label — an operator's, or a downgrade rule's — carries the ladder plus whatever else it means to say. A downgrade rule is therefore **overlaid** on the derived label rather than compared with it: read as-is, every dimension the rule stayed silent about looks like a tightening, so a rule relaxing one dimension could never be written without restating all of them — which is how a second dimension gets changed by accident. Regressions: `test_a_derived_label_carries_every_dimension_even_an_undeclared_one`, `test_an_absent_dimension_and_an_empty_one_are_told_apart_by_declares`, `test_a_rule_says_nothing_about_the_dimensions_it_omits`.
- **An unlabelled SOURCE column fails propagation; it does not fall to deny-by-default.** Deny-by-default is the reading of a source column nobody labelled, and it is applied where the source is declared (the bullet above). By the time propagation runs, a source column with no label means lineage and labels disagree about what was read — and composing the ones that happen to be present publishes a ceiling computed from a subset of the inputs, which looks exactly like a correct answer. Same stance on a lineage edge naming a source nothing labelled, on propagating an asset with no labelled input at all, and on two source columns differing only by case. Regressions: `test_an_unlabelled_source_column_fails_rather_than_counting_as_unrestricted`, `test_lineage_from_a_source_nothing_labelled_fails`, `test_propagating_with_no_labelled_input_at_all_is_refused`, `test_source_columns_differing_only_by_case_are_refused`.
- **A column with no declared lineage falls back to the TABLE MAX, never to nothing.** A Python asset that declares no `TableColumnLineage` has read the whole table as far as anyone can prove, so every output column carries the composition of every labelled column of every source read; `Propagation.table_max_columns` names them so an operator can see what declaring lineage would buy. Composing *no* labels at all is refused outright — the least restrictive label in every dimension is the one answer that must never be arrived at. Regressions: `test_a_column_with_no_declared_lineage_falls_back_to_the_table_max`, `test_composing_no_labels_at_all_is_refused`.
- **A downgrade is refused unless it is accountable AND it actually relaxes.** A rule with no named owner, no reason, no columns, a label the document does not declare or a label missing the ladder is refused rather than recorded; so are two rules for one column (which one the aspect credits decides who is accountable), a rule aimed at a column the asset does not produce (a permission nobody is watching, left behind by a rename), a rule that tightens any dimension (it would be recorded as a release of data that was never released, and a reader denied by it would have no rule to appeal to) and one that changes nothing (it tells an auditor a downgrade happened when none did). Every application records the rule, owner, reason and **both** labels — an aspect carrying only the published one cannot be checked against what the data derived. Regressions: `test_an_applied_downgrade_records_the_rule_owner_reason_and_both_labels`, `test_a_standing_rule_with_no_named_owner_fails`, `test_a_declared_downgrade_with_no_reason_fails`, `test_a_rule_that_tightens_a_dimension_is_not_a_downgrade`, `test_a_rule_that_tightens_only_a_set_dimension_is_still_refused`, `test_a_downgrade_that_changes_nothing_is_refused`, `test_a_rule_aimed_at_a_column_the_asset_does_not_produce_fails`, `test_two_rules_for_one_column_are_refused_rather_than_ordered`.
- **The engine is pure, asserted — and the assertion has to put `sys.modules` back.** `test_the_engine_imports_no_dagster_no_datahub_no_warehouse` evicts `dag_tools.warehouse_source*` and re-imports to see whether `dagster` / `datahub` / `sqlalchemy` / `dlt` appear. A module re-imported under the same name is a **different module object**, so every class it defines is a second class: without the restore, another module's `pytest.raises(DimensionsError)` stops recognising the exceptions this package raises, and only in a run where this test happens to go first. The test restores the evicted modules in a `finally` and asserts the restore.
- **The observation moves no data, and its statements are the operator's.** Default statements count rows and name columns and nothing else; an as-of statement is optional and, when declared, is sent verbatim. The row count is read **positionally and exactly** — no float path, so it is right past 2**53 — a grouped count is refused rather than summed, an as-of that comes back absent is refused rather than recorded as empty, and a relation carrying a statement separator fails the load. The schema hash is order-sensitive: a reordered table is a changed table.
- **Nothing in the package or the component names a database, schema, table, column, dimension or value** — not as a constant, not as a default, not in a comment. The hierarchical dimension is discovered from the document's own flag. The example's vocabulary belongs to its sqlite file and says so; `examples/warehouse_source` runs end to end with no warehouse and no credentials, loads on the 1.10.19 floor, and spells every variable as `{{ env('X') }}` because the attribute form does not resolve there (§4j).

### 4n. Classification propagation (`dag_tools.components.classification_propagation` + `ClassificationPropagationComponent`)
*Steps 4b/4c of ADR-0064. 4m labels a source, where a human decided what the labels ARE; this labels everything downstream of it, where nobody decides anything, because the label of a derived column is a consequence of what it read. The composition engine is 4m's pure `propagate.py`; this is the Dagster surface over it. One sensor, no assets.*
- **The source-side lookup reads the OBSERVATION log as well as the materialization log, and the derived side must not.** A 4a source is an *observable source asset*: observing it emits an `AssetObservation` and never a materialization, so a materializations-only lookup finds nothing on any real 4a source and every propagation refuses with "publishes no label set" — a wiring failure wearing a labelling failure's words. Storage ids are one sequence, so "newest across the two logs" is well defined, and `EventLogRecord` answers `None` for whichever event it does not hold, so one reader covers both (`_latest_published` / `_event_metadata`). The **derived** side stays materializations-only on purpose: this sensor writes its own `AssetObservation` against the derived asset, and counting that would make the newest event one the cursor's banked storage id can never match, republishing the dataset on every tick forever. Found by building the shipped example and running it; no unit test that reported its own source event as a materialization could see it. Regression: `test_the_shipped_example_propagates_from_a_source_it_only_OBSERVED`.
- **The sources are DECLARED, never inferred from the asset graph.** Which upstreams publish a label set is a policy fact, not a graph fact. Inferred, an upstream publishing none would look like nothing to propagate from, the ceiling would be composed out of a subset of the inputs, and the result would look exactly as correct as the real answer. So `sources:` is required per dataset, a lineage dep naming a source not listed there is refused, and a listed source with no published label set fails that dataset rather than contributing nothing.
- **Composition tightens only, and the directions differ — see §4m.** `max` on the hierarchical dimension, union on a restrictive or exclusionary set, **intersection** on a permissive one. Nothing in this component re-implements that; it calls the pure engine, which is what keeps the semantics testable with no Dagster and no catalog.
- **A column with no lineage entry publishes the TABLE MAX, and composing no labels is refused.** The fallback is the whole table's ceiling — every labelled column of every source read, deny-by-default columns included — and the published decision records which basis it used (`column_lineage` or `table_max`) plus the exact source columns, so a coarse label reads as coarse rather than as wrong. Composing zero labels is refused outright: the least restrictive label in every dimension is the one answer that must never be arrived at.
- **A downgrade is the only thing that can widen a column, so it is accountable and it is overlaid.** `id`, `owner` and `reason` are required and the id travels on the published decision; two rules reaching one column are refused rather than ordered (which one the record credits decides who is accountable); a rule that tightens any dimension is refused as a re-label. A dimension the rule omits keeps what the data derived, and an **empty set clears** that dimension — an empty set is a value, not an omission, which is the round trip that lets a rule release a restrictive or exclusionary facet at all (§4l's empty-set rule). Rule labels are validated against the mounted document at the **load**, not at the first tick: a typo in a governance decision is not something to discover after a deploy. Regression: `test_a_declared_downgrade_is_validated_against_the_document_at_load`.
- **Published as exactly TWO patch aspects, never a replace.** `datasetProperties` (`classification`, `classification_origin: propagated`, the sources, the document digest) then `editableSchemaMetadata` — a glossary term per column per label value **plus a `remove` for every other term in the vocabulary**. Add-only would leave a stricter term behind and silently void the downgrade; a full aspect would wipe a crawler's metadata. Same `EditableSchemaMetadata`-not-`schemaMetadata` reasoning as §4m, and as in §4i no `token` key is emitted when there is none.
- **Stopped by default, re-read every tick, isolated per dataset, retried without re-materializing.** Publishing classifications is not something a deployment starts doing because a code location loaded, so `default_status: STOPPED`. The dimensions document is re-read on **every tick** because a ConfigMap can move between a deploy and a tick. One dataset's failure is recorded against that dataset and never stops the others, and a failing dataset is retried on later ticks against the same materialization — so a corrected rule publishes on the next tick with no rebuild. An absent document loads and fails the **tick**, same split as §4m. `dry_run` composes and records everything and emits nothing. Regression: `test_the_code_location_loads_with_no_document_mounted`.
- **Chained propagation is NOT supported.** A derived dataset cannot be another's source: this component records its decisions as observations against the derived asset and reads its *sources'* published label sets. Documented in the README and the example rather than half-built.
- **YAML trap, worth knowing before you edit an example: a block key present with only comments under it parses as `None`.** The component's `catalog` attribute is `Dict[str, Any]`, which rejects it — so an unset block needs its **key** commented out too, not just its contents. The example says so inline. The attribute is deliberately not loosened, to match 4a's component.
- **The example is part of the contract, and `examples/warehouse_source` now carries both halves.** The derived asset (`dagster_home/derived.py`) is ordinary Python, not a dag-tools component, which is the premise: what builds a derived table is the deployment's business and all the propagation needs is the `dagster/column_lineage` Dagster already carries. Its three columns are the three outcomes (lineage; lineage then downgraded; table-max fallback). Tests go through the shipped example copied into tmp under a per-test package name — `build_component_defs` imports the components directory as a module, so two tests loading two copies under one name both get whichever reached `sys.modules` first, and the *parent* of that directory has to be importable as well.

### 4k. Contract mapping (`dag_tools.contract_mapping` + `ContractMappingComponent`)
- **The engine is pure, and that is what makes the mapping semantics testable.** No Dagster, dbt or dlt imports and no IO in `dag_tools/contract_mapping/`: documents in as dicts, a `MappingPlan` out. The component, the SQL route (`render_dbt_artifacts`) and the row route (`apply_to_rows` / `check_rows`) all share one plan. The row route exists so a mapping can be proven with no warehouse — `test_contract_mapping_proof.py` runs the shipped mapping over rows derived from the shipped fixture and asserts it reproduces it exactly, types included, by **inverting every transform the plan declares**. The inversion is generic (it reads `plan.columns`, so it names no column) and it fails if the plan's description of a transform ever stops matching what the row renderer does with it — the one disagreement that would make a dry run a lie. Regression: `test_the_mapping_reproduces_the_fixture_exactly`.
- **A refusal is "the emitted artifact would be WRONG"; everything else is a note.** A mapping that reads a column the source does not have, drops a column a governed read selects (required, grain or scope), or disagrees with the contract about write cadence fails the **code location load** — before any run. A mapping that cannot get a test written (the contract names its period calendar instead of listing it; no `warehouse_types`; no `non_finite_predicate`; a `constant_within` over an unproduced column) loads and says so in `plan.notes`: the model is correct, there is just less proof of it than there could be. Every problem is collected rather than raised on the first one, because an operator fixing a mapping wants the list. Regressions: `test_contract_mapping_plan.py` — `test_every_problem_is_reported_at_once`, `test_a_cadence_disagreement_is_refused_because_it_fails_silently`, `test_a_named_but_unlisted_calendar_gets_no_test_and_says_why`, `test_no_warehouse_types_means_no_enforced_contract_and_says_so`.
- **Guess nothing to fill a gap.** There is no default warehouse type, no default cast template, no default non-finite predicate and no inferred period calendar. Each wrong guess emits SQL that fails at the warehouse for a reason that has nothing to do with the data, and a guessed `non_finite_predicate` silently matches nothing — a test that passes without checking anything is worse than a note saying it was not written. `config.contract.enforced` is emitted only when **every** column has a declared warehouse type; one missing type drops the whole contract rather than half of it, because a half-enforced contract reads as an enforced one. Regressions: `test_one_missing_warehouse_type_drops_the_contract_rather_than_half_of_it`, `test_the_contract_is_enforced_only_when_every_column_has_a_warehouse_type`.
- **A file contract is reconciled at load; a served contract is fetched at materialization.** A code location must not fail to load because a service is down, so the served route does its fetch in the run and says so in its notes rather than implying the load-time check ran. `expect_contract_id` is what stops a service that starts serving a different document from silently re-pointing the mapping, and it is worth setting on the file route too, where it catches a path edited to the wrong document — every column name might still line up. Regressions: `test_a_served_contract_is_not_fetched_at_load`, `test_a_served_contract_is_fetched_at_materialization`, `test_the_expected_contract_id_is_enforced`.
- **Render everything into memory, then write.** A dry run shows the exact bytes (and `dry_run` in run config overrides a configured target for one run, which is how a mapping change is reviewed), and a render that fails leaves the target directory untouched rather than half-rewritten. `prune` is **off by default** and only ever considers files named `<model>__...`: this component writes into a directory it does not own, and deleting a test an operator wrote by hand is worse than leaving a stale one. Regressions: `test_nothing_is_written_when_the_render_fails`, `test_prune_is_off_by_default_so_a_hand_written_test_survives`, `test_prune_removes_only_files_this_component_would_have_written`.
- **Type fidelity is the hard edge, and the failure mode is silent.** Integer text parses exactly past 2**53 (never through `float()`); a `numeric` column keeps the source's **written form**, so a whole amount does not widen into `1.2e6`, which reads as the same number and is not; a non-finite value is refused with the field path rather than rendered; a boolean in a numeric column is refused rather than counted as 1. `factor` on `scale` is read as a `Decimal` — a unit conversion of money through a binary float is how a total stops reconciling. Regressions: `test_contract_mapping_emit.py` — `test_integer_text_parses_exactly_past_float_precision`, `test_a_numeric_column_keeps_the_sources_written_form`, `test_a_non_finite_value_is_refused_and_the_message_names_the_field`, `test_scale_renders_the_factor_as_written_not_as_a_float`.
- **Hazard: a SQL cast ROUNDS where the row route REFUSES.** The row route rejects a scaled value that is not whole (`test_a_non_whole_value_into_an_integer_column_is_refused_not_rounded`); `cast({expr} as <integer type>)` rounds in most dialects. The cast is the operator's own SQL from `cast_templates` and this library owns no dialect, so this is **documented** (the example README) rather than papered over — same stance as the `--empty` vacuous-tests hazard in 4i. Do not "fix" it by rounding the row route to match; if silent rounding is unacceptable, the cast is where the check goes. The cast must also wrap the **whole expression**, not the source column: what needs correcting is the type the transform produced. Regression: `test_the_scaled_columns_carry_a_cast_so_the_contract_can_be_enforced`.
- **Every emitted test fails under a rule the contract declares.** A failure naming an id outside the contract's `rules:` cannot be acted on by anyone reading the contract, so `tests_under_undeclared_rules` is a number on every materialization, every singular test carries its rule id in a comment **and** as a selected column, and the key-uniqueness id is derived structurally from the contract's grain rather than written down in this library. A mapping may override an id; an override naming a rule the contract lacks is still flagged. Regressions: `test_every_emitted_test_fails_under_a_rule_the_contract_declares`, `test_the_key_uniqueness_id_is_derived_from_the_grain_not_written_down`, `test_an_override_naming_a_rule_the_contract_lacks_is_still_flagged`.
- **The asset of record is the PHYSICAL platform's dataset URN**, taken from the contract — never a `dagster` platform URN. The mapped model is what a governed read is served from, so that is the object the catalog registers and the object a broker authorizes; the raw table's URN and the Dagster asset attach as **lineage**. Regression: `test_the_materialization_records_the_physical_platform_as_the_asset_of_record` (it also asserts `asset_of_record != source_dataset`, so a plan that collapsed the two would fail).
- **A contract's forward-declared columns are reported, never demanded, and the empty report is PUBLISHED rather than omitted.** A contract declares columns ahead of their producer so readers can be written against them (`produced_since: null`), so a mapping is not wrong for leaving them unmapped — but the forward edge stays visible in `unmapped_declared` and on the materialization, and producing one is noted as a contract edit. The shipped example has **no forward edge left** since the fixture gained `status_period` and `eac_reported`, so its assertions are the empty case and would pass vacuously if the key were simply absent: an operator who finds no `declared_not_produced` cannot tell "nothing is forward-declared" from "this plan does not track it". The non-empty case is therefore proven twice over — on the engine by `test_contract_mapping_plan.py`'s synthetic contract (whose baseline carries one unmapped declared column on purpose, so every note assertion in that module stays unambiguous), and on the component by re-opening the edge on the **copy** of the example. Regressions: `test_the_examples_forward_edge_report_is_published_EMPTY_not_omitted`, `test_a_forward_declared_column_is_reported_by_NAME_rather_than_hiding_it`, `test_the_example_produces_every_column_its_contract_declares`, `test_every_column_the_fixture_carries_is_recorded_as_produced`, `test_producing_a_forward_declared_column_is_noted_as_a_contract_edit`.
- **`produced_since` is the ONE field dag-tools' own release moves in the vendored contract.** It names the dag-tools release whose fixture carries the column, so the fixture gaining a column is what sets it — which means a fixture change edits a *governed* document and the upstream copy needs the same token. That is what the drift canary below is for; nothing else in that file is ever edited on this side. The chain is forced, not optional: `test_contract_mapping_proof.py` asserts the plan's output columns are exactly the fixture's columns, so a fixture column obliges the example mapping to produce it, and producing a column the contract calls unproduced puts a note on the plan that `test_the_example_mapping_leaves_the_plan_with_nothing_to_report` refuses.
- **Stay inside `type:` + `attributes:` with plain dict/scalar fields** validated against sibling pydantic models with `extra="forbid"`. Same floor discipline as 4j: no nested `Resolvable`, `{{ env('X') }}` never `{{ env.X }}`, no `from __future__ import annotations` in the component module (it turns a `config:` parameter's annotation into a string and Dagster then reads it as an asset input). Verified on the 1.10.19 floor by **running** the whole module set there — identical 92 passed / 1 skipped, same `plan_hash` — not by reading the code.
- **The vendored contract is byte-identical to upstream, and the canary skips rather than guessing.** `examples/contract_mapping/contracts/ev_fixture.yaml` is governed in the agent repo and vendored here with **no added header**, so the comparison stays a byte comparison; provenance lives in the example README instead. `test_the_vendored_contract_has_not_drifted_from_upstream` compares when `DAGTOOLS_UPSTREAM_EV_CONTRACT` or a sibling checkout points at the upstream copy and **skips** otherwise — a canary that silently passes when it cannot find its target is worse than no canary.

### 4j. Read audit and the tagged warehouse (`dag_tools.audit` + `ReadAuditComponent` + `TaggedWarehouseComponent`)
- **The component is the primary surface; the CLI is an extra door.** A deployment configures the audit by writing `component.yaml`, not by running a command — the standing rule in Dagster's vocabulary. `dagtools audit` exists for the operator who has an export and a terminal and no deployment yet, and it must stay a thin wrapper over the same engine. Do not grow behaviour into the CLI that the component cannot express.
- **Nothing in `dag_tools.audit` names a relation, a column, a level or an identity — not even as a default.** Every warehouse spells its query history differently and the operator's account may expose it through a view of their own, so `HistoryColumns` has five required fields and no fallbacks. A default would be a name in this repo, and a *wrong* default is the dangerous kind: it would audit the wrong column and report an empty window as a clean audit. Regressions: `test_nothing_in_the_audit_package_names_an_object` (every `HistoryColumns` field is required), `test_reading_through_a_resource_demands_every_column_name`.
- **The statement is built, never executed, and only identifiers are interpolated.** `build_history_statement` returns SQL plus bound (`:named`) parameters; the component hands both to a resource's `fetch_rows`. Same split and same reason as `otel_api_sync._staging_url` — resolution is the part this module decides, and a test that opened a connection would die on a driver CI does not install. An identifier cannot be bound, so `validate_relation` whitelists one to three unquoted dotted parts and **refuses** anything else rather than escaping it; the column names go through the identical grammar because they are interpolated too. Regressions: `test_every_value_is_bound_and_none_is_interpolated`, `test_anything_that_is_not_an_identifier_is_refused_not_escaped`, `test_a_column_name_goes_through_the_same_grammar`, `test_the_component_executes_nothing_itself`.
- **Only the tag's principal is tested against the `pipeline:<name>` grammar — never the history row's.** This was wrong once and the bug was invisible to review: a warehouse username never matches that grammar, so every untagged read was reported as `not_a_pipeline` and the whole correlation branch was **dead code**. A row's identity is in the warehouse's namespace, not ours; narrowing the audit to the service identity is the operator's `principal_filter`, not an inference to draw from an opaque credential name. An unrecognised kind *inside* a tag still denies, because the tag is ours and a kind we do not know is a contract break. Regressions: `test_an_untagged_read_correlates_through_one_single_asset_window`, `test_an_opaque_row_identity_is_not_evidence_either_way`, `test_an_unknown_principal_kind_in_a_tag_is_not_a_pipeline`.
- **The gap is the deliverable, and it is published decomposed.** A read nothing explains stays in `unexplained_relations` *and* is broken out into `ambiguous_relations` / `untagged_relations` / `non_pipeline_relations`, because the three go to different people: untagged closes by deploying the tagged resource (step 2), ambiguous by narrowing a run's selection, and a non-pipeline read is not an attribution gap at all — what a person may read is a brokering decision. Never collapse them into one number, and never attribute a read to a plausible neighbour: a run that materialized two assets explains neither. Regressions: `test_a_multi_asset_run_cannot_attribute`, `test_the_gap_contains_every_read_no_asset_explains`, `test_the_metadata_decomposes_the_gap`.
- **`coverage` is `None` on an empty window, and the metadata omits it entirely.** 0/0 is not full coverage. A window the audit saw nothing in reporting 100% is the shape of every vacuous pass this project has had to go back and fix (the preflight sha check, the staging-need `None != []` rule, `--empty` making dbt tests vacuous). Likewise a malformed history row lands in `row_failures` rather than being dropped, because dropping rows under-reports the gap — the one direction this tool must not be wrong in. Regressions: `test_coverage_is_none_when_nothing_was_read`, `test_one_malformed_row_is_reported_not_swallowed_and_not_fatal`.
- **`fetch_rows(statement, parameters)` is the entire resource seam**, and it is what step 2's tagged warehouse resource implements. One method keeps a driver out of CI, a credential out of this repo, and lets the tagged resource drop in underneath without touching the component. A resource missing the method fails with a pointed error naming it, not an `AttributeError` mid-materialization. Regression: `test_a_resource_without_fetch_rows_fails_with_a_pointed_error`.
- **The 1.10.19 compat floor holds, and is held deliberately.** Measured: the shipped example loads *and* materializes on `dagster==1.10.19` with numbers identical to current, and the whole audit suite is green there. What that version forbids is an **unknown top-level key in a component file** — `post_processing` is a sibling of `type:`, the floor's model forbids extras, and the rejection fails the *entire* code-location load rather than just that block (the otel finding, gated in `85b3b49`). So this component file stays inside `type:` + `attributes:`, and every component field is a plain dict or scalar validated against pydantic models in `schema.py` rather than a nested `Resolvable`. That indirection is the price of deployability on the floor; a malformed block still fails the load with a pointed error, which is the property that mattered. Regressions: `test_the_component_file_uses_no_top_level_key_beyond_type_and_attributes`, `test_every_component_field_is_a_shape_the_floor_resolves`, plus the error-matched skip gate `_skip_if_the_component_file_is_refused` so a future refusal is reported rather than hidden.
- **No `from __future__ import annotations` in `read_audit/component.py`.** The asset's `config: ReadAuditRunConfig` parameter must be a real class object at definition time or Dagster raises `DagsterInvalidPythonicConfigDefinitionError` naming the string. Same trap already documented in `grist_ingest.component`; it cost eight failures here.
- **The example is part of the contract.** `examples/read_audit` runs with no warehouse and no credentials (a synthetic export), and `test_read_audit_component.py` loads it through `build_component_defs` exactly as a deployment would. Building that example is what found both real defects in this module — the dead correlation branch and the future-import trap — neither of which any unit test as written would have caught.
- **The seal is the point of `TaggedWarehouseResource`: a query issued through it either carries its attribution or is not sent.** `plan_tagged_query` refuses an empty tag, and `execute_plan` re-checks `plan.carries_tag` at the one chokepoint that touches a connection -- two layers, because a later edit that builds a plan without going through `plan_tagged_query` would otherwise send a bare read. The refusal is also ordered **before** connection resolution, so a misconfigured connection can never mask a missing principal. `pipeline_name` stays optional (an on-behalf-of resource binds its principal per request), which is what keeps the seal a reachable configuration rather than a test-only state. Regressions: `test_a_query_without_a_principal_is_refused_not_sent` asserted twice -- once against a connection factory that raises, once against a monkeypatched `_engine` -- plus `test_the_refusal_happens_before_any_connection_is_resolved` and `test_execute_plan_refuses_an_untagged_plan`.
- **`InitResourceContext` has no asset key -- measured, not assumed -- so the resource self-tags the run and `for_asset(context)` sharpens it.** The context a resource is initialized with exposes `run` / `dagster_run` / `run_id` and **no** `asset_key`, `op_def` or `step_context`, so a resource cannot know on its own which asset is reading. `fetch_rows` therefore tags `{principal, run_id}`, which the audit resolves only when the run selected exactly one asset; an asset that wants `BY_ASSET_KEY` attribution calls `for_asset(context)` (one line) and a read made for a person uses `for_user(authz_id)` with the authz_id the gateway verified. Pinned against the real Dagster classes by `test_the_fixtures_match_what_dagster_offers`, so a version that grows the attribute fails the test instead of leaving a stale workaround in place.
- **A JSON tag in a SQL comment collides with SQLAlchemy's bind parsing, and only running the example found it.** `sqlalchemy.text()` reads `:1` as a bind parameter, and the tag contains `"schema_version":1` -- so **every** comment-placed read died at submission with `A value is required for bind parameter '1'`. Invisible to any unit test that stubs the transport. `escape_tag_comment` escapes the colons inside the generated leading comment and nothing else (the comment is located by its closing marker, which a tag may not contain), and the backslashes are stripped at compile time so the warehouse receives the tag byte for byte. Regressions: `test_a_comment_placed_tag_round_trips_through_sqlite`, `test_the_escape_never_reaches_the_warehouse`, `test_the_escape_leaves_the_callers_own_parameters_alone`.
- **The connection has no environment fallback and is resolved at load.** There is no magic variable name to fall back to: one would belong to whichever pipeline set it last, and a resource that silently connected somewhere else would produce a confident report about the wrong account. `connection:` must name a `dsn` or a `drivername` + parts, and `ConnectionBlock._resolves` calls `warehouse_url` during validation -- safe because resolution returns a URL string and builds no engine, so no driver is imported while a code location loads (the `_staging_url` split again). An operator's typo fails the load, not a 3am materialization. Regressions: `test_a_connection_naming_nothing_fails_the_load`, `test_no_environment_variable_stands_in_for_a_connection` (four plausible env vars set, refusal unchanged).
- **The library ships no tag dialect.** `placement: comment` needs nothing; `placement: session` runs the operator's own statement, which must bind `:tag`, be a single statement, and carry no comment marker -- validated by one `TagTransport` used both at load and at query time. Guessing `ALTER SESSION SET QUERY_TAG` would be a vendor name in a library that is not allowed to name anything. A statement that does not bind `:tag` is the dangerous case, because it runs happily and attributes every later read to nothing; it fails the code-location load instead. Regression: `test_a_tag_statement_without_the_bound_tag_fails_the_load_not_the_run`.
- **`{{ env.X }}` does not resolve on the 1.10.19 floor; `{{ env('X') }}` does.** Measured by loading this example on both: on 1.10.19 `env` is a plain function in the template scope, so the attribute form raises `UndefinedError: 'function object' has no attribute TAGGED_WAREHOUSE_DB` and, like an unknown top-level key, takes down the whole code-location load; 1.13.1 accepts either spelling. The call form works on both, so every reference in `examples/tagged_warehouse` is spelled as a call. The repo's older examples use the attribute form and make no floor claim — if one ever needs to, this is the edit. Regression: `test_the_example_names_env_vars_the_way_the_floor_resolves_them`.
- **Resolving the connection must not import `dlt`.** `warehouse_url` first routed through `config_to_credentials`, which lives beside the dlt asset factory — and `dlt` ships in the `orchestrator` extra, not in the core dependencies. So on any install without that extra the resource could not resolve a connection at all: nine failures on the floor venv, `ModuleNotFoundError: No module named 'dlt'`, in a suite that was green on a machine where dlt happens to be installed. SQLAlchemy's `URL.create` does the same job (and the same percent-encoding of user info) with a dependency the resource already has. The shape of the `connection:` block is unchanged — a `dsn` or the familiar parts — so this is a resolver swap, not a config change. Regression: `test_resolving_a_connection_does_not_import_dlt`, asserted in a subprocess because the development interpreter has already imported dlt for something else.
- **The drop-in is proven end to end, not asserted.** `examples/tagged_warehouse` runs step 1's `ReadAuditComponent` **unchanged** over this resource by key (`fetch_rows` is still the whole seam), against sqlite, with no credentials. `test_the_resource_drops_in_under_an_unchanged_read_audit` materializes it and checks the exact per-method counts -- one read explained by asset key, one untagged, one carrying another tool's tag -- so a change that collapsed one cause into another shows up as a wrong number rather than a passing test. The fixture tag is read off a plan the shipped resource built, so writer and reader cannot drift apart silently.
- **The concurrency cap's wait lives inside the `ctx.run` action, and the permit outlives the coroutine.** `api.max_concurrency` bounds requests in flight per worker process, per `base_url`: the effective cap at the API is `max_concurrency × restateWorker.replicas`. Seven things are load-bearing, all measured on Restate 1.6.2 / 1.8.1 and SDK 0.14.2 (`docs/RECIPE.md`, "OTel → API sync: concurrency and Restate's timeouts"). (1) The wait is inside the action, because the SDK calls the action only when it executes the step, so a replay never waits for a permit; waiting outside the step does not escape Restate's timers and would repeat on every replay. (2) The permit is released from the `concurrent.futures.Future` done-callback (`loop.call_soon_threadsafe`), never by `async with`: the SDK cancels the action's task when an attempt ends, and cancelling a task awaiting an executor future leaves the thread running, so an `async with` release hands the permit on while the abandoned request is still in flight and the cap overshoots. (3) The cap is per process and multiplies by replicas; a cluster-wide limit is out of scope. (4) Crossing the inactivity timeout alone is harmless; inactivity + abort is the real bound, and a request *in flight* when the abort fires is the duplicate (a call merely parked sends nothing). (5) So the action refuses to start a request it cannot finish: it waits for a permit at most `inactivity + abort − timeout_seconds − margin` and otherwise raises a retryable error before sending. A deadline ≤ 0 is never "no deadline". (6) The service's timeouts come from `API_CALL_PLAN_INACTIVITY_TIMEOUT_SECONDS` / `API_CALL_PLAN_ABORT_TIMEOUT_SECONDS`, and the kwargs are passed **only when set**: SDK 0.14.2 negotiates discovery v2 and `compute_discovery_json` raises `ValueError` for them there, which fails registration and leaves the worker serving nothing. Unset keeps discovery identical to before. (7) One `requests.Session` per thread (`threading.local`), `trust_env` left on so `REQUESTS_CA_BUNDLE` still applies; `test_session_requests_still_honour_REQUESTS_CA_BUNDLE` pins it. An exhausted retry bound (`max_attempts` / `max_retry_seconds`) raises `TerminalError` from `ctx.run`; it is caught at all three `_run_call` sites and recorded as `FAILED`, never raised. `PLAN_FORMAT_VERSION` is not bumped, so an older worker ignores the cap silently. Live regression: `test_restate_concurrency_e2e.py` (`DAGTOOLS_E2E_RESTATE=1`).

### 4i. dbt -> DataHub publishing (`CustomDbtProjectComponent`)
- **Every `dbt.cli()` call in `execute()` MUST share one `target_path`.** `DbtCliResource.cli()` mints a fresh `target/<op>-<run>-<uuid>` directory per invocation unless handed an explicit `target_path` (dagster-dbt's private `_get_unique_target_path`). The DataHub recipe names `manifest.json` / `catalog.json` / `sources.json` / `run_results_build.json` relative to a *single* cwd, so an unpinned invocation silently strands its artifacts in a directory `datahub ingest` never looks at. The real failure was `FileNotFoundError: [Errno 2] No such file or directory: './sources.json'`, because only `dbt source snapshot-freshness` writes sources.json and it was the one call left unpinned. Regressions: `test_dbt_artifacts_are_not_scattered_across_target_directories` and `test_every_artifact_the_datahub_recipe_names_is_in_the_ingest_cwd`.
- **`docs generate` clobbers `run_results.json`.** The build's results are what carry materialization lineage into DataHub, so they are copied to `run_results_build.json` *before* docs generate runs, and the recipe reads that copy. Don't "simplify" the recipe back to `run_results.json`. Regression: `test_run_results_from_build_survive_docs_generate`.
- **`_publish_to_datahub` swallows every failure by design** — a DataHub outage must not fail the dbt build — which also means no unit test that only asserts "execute() didn't raise" can see ingestion break. That is precisely how the scattered-artifacts bug shipped. Assert on artifacts and on what DataHub received, never on the absence of an exception.
- **A DataHub PAT is required whenever the GMS runs with `METADATA_SERVICE_AUTH_ENABLED=true`** — which the sandbox cluster does. `_publish_to_datahub` resolves it the same way `DatahubLineageComponent` does: explicit `datahub_config.token`, else the standard `DATAHUB_TOKEN` env var (the deployment already wires it from `iagent-secrets`). Omitting it fails in a genuinely misleading way: `infer_dbt_schemas` reads `schemaMetadata` back out of GMS *before* emitting, so the 401 surfaces as a source-side `HTTPError` with `produced 0 events`, not as a sink auth error. Verified live against the cluster GMS — 3 failures / 0 events without the token, 0 failures / 16 events with it. Emit **no** `token` key when there is none; `""` is sent as a credential and rejected.
- **The example is part of the contract.** `examples/real_declarative_dbt` pointed at two dbt projects that did not exist in the repo, so the one worked example of this component could never load — which is why the path had never run anywhere, and why the deployed `dag-tools` code location still builds no dbt assets at all (`dag_tools/user_deployment/definitions.py` has zero dbt references; its `datahub_config` is the lineage *sensor*). `test_example_dbt_projects_resolve.py` fails on a dangling `project:` path.
- **`dbt docs generate` must NOT be given a Dagster context.** dagster-dbt appends the context's selection (`--select fqn:*`) to any invocation it is handed one, and that selection does not match sources — so the catalog came out models-only and DataHub warned `Node missing from catalog: source.<project>.<table>`, silently dropping source column schema. A catalog describes the *project*, not the run. Contextless also means `.wait()` instead of `.stream()`, which removes any chance of re-emitting materializations the build already yielded. Regression: `test_docs_generate_is_not_given_a_context`.
- **The demo dbt surface is the deployed exercise, and it is demo-gated.** `dag_tools/user_deployment/demo_dbt_assets.py` registers a seed→model→model project ONLY under `DAG_TOOLS_DEMO_MODE`; production must not grow synthetic tables or publish demo lineage to a real DataHub. It uses **seeds, not sources**, because `execute()` runs freshness *before* build — a source would need a raw table that nothing has created yet, so the demo would fail on every clean cluster. It builds through public `@dbt_assets` + `execute()` rather than `build_defs`, to avoid depending on `StateBackedComponent` state plumbing and the private `_project_manager`; and it constructs the component through the **dataclass**, never `__new__`, since bypassing `__init__` leaves inherited fields like `include_metadata` unset and the base `execute()` then dies mid-materialization. Every failure degrades to empty `Definitions` — an exception here would take the whole code location down.
- **The three-invocation scoping is load-bearing, and `--empty` rides on it.** `cli_args: ["build", "--empty"]` (the dagster-dbt field) is the supported way to make the Q2 staging build schema-only, and it is safe only because `execute()` passes `get_cli_args()` to the **build** call alone; freshness (`["source", "snapshot-freshness"]`) and docs (`["docs", "generate"]`) are hardcoded. `--empty` exists on dbt `build` / `compile` / `run` only; `docs generate`'s lookalike is `--empty-catalog`, a different flag. `DBT_EMPTY=true` is the env-var form and is inert on the other subcommands (dbt declares it as an alias LIST, observed `['DBT_ENGINE_EMPTY', 'DBT_EMPTY']`, and click takes whichever is set first -- the canary asserts membership, never equality). Never DRY the three calls into one args list, and never route `--empty` through global flags (`dbt --empty build` is invalid). **Hazard:** under `--empty` dbt tests pass vacuously on empty relations, so Q6 asset-check parity is not evidence of data correctness (see `docs/RECIPE.md`, "Staging data for Q2"). Regressions: `test_resolved_cli_args_reach_only_the_build_invocation`, `test_the_non_build_invocations_are_hardcoded_and_unparameterized`, `test_empty_is_not_a_global_config_flag`, `test_empty_makes_dbt_tests_vacuous_is_documented`, and the real-dbt canaries `test_dbt_accepts_empty_on_build_and_not_on_docs_generate` / `test_dbt_empty_env_var_is_the_documented_name`.
- **This path is only trustworthy under an end-to-end run.** `dag_tools_tests/test_dbt_datahub_e2e.py` (`DAGTOOLS_E2E_DBT=1`, needs docker) runs real postgres + the real dbt CLI + the real `datahub` CLI against an in-process GMS recorder. The GMS is stubbed *only* because a real one needs Kafka/Elasticsearch/MySQL, and the artifact handoff fails on the ingestion **source** side, long before the sink. Note the stub must answer `404` on `GET /aspects/...` — `infer_dbt_schemas: true` looks up each target dataset's `schemaMetadata`, and a `200 {}` makes the client raise `GraphError` instead of treating the aspect as absent.

### 4h. Verdict (`dag_tools.qual.verdict`)
- **Metadata parity is KEY-set only.** The recipe is explicit that metadata *values* may differ between baseline and candidate (different timestamps, different run IDs in materialization metadata). Gating on values would NO_GO every qualification. The check compares `set(record.metadata_keys)` on each side; `test_diff_compares_metadata_KEY_set_not_values` is the regression. Don't add value comparison without an opt-in flag.
- **Duration deltas are informational.** A 10x slower candidate is operator judgment, not a verdict gate. We compute `duration_delta_s` for visibility, but it never influences `is_pass`.
- **Strict by default; operator opts into gaps.** Q6 v1 can't auto-evaluate orchestration snapshots, synthetic probe coverage or round-trip coverage (`--accept-roundtrip-missing`). Rather than silently treating "absent" as "passing," `GapAcceptance` defaults every gap to False, blocking GO until the operator explicitly accepts each one with an `--accept-*` flag. New gaps follow this pattern.
- **Candidate-preflight failure is the one absolute hard gate.** No `GapAcceptance` override exists for it. If preflight failed, operators fix the deployment — they don't paper over it. The regression test `test_verdict_no_go_when_candidate_preflight_failed` runs with EVERY accept flag on; verdict still NO_GO.

### 4g-1. Probe deploy-state status (`dag_tools.qual.probes.status`)
- **The location name is HARD-CODED to `dag-tools-probes`** — same constant the runner uses (`PROBES_LOCATION_NAME`). Both modules import from one source; if you ever make it configurable, do it via the manifest (operator's deploy contract is fixed across a qual_id), never via per-call override.
- **`ABSENT` is a distinct state from `LOADED`-but-empty.** The status module reports `ABSENT` when the workspace doesn't even have a `dag-tools-probes` entry; that's the diagnostic signal the operator forgot to register the location. Don't silently treat ABSENT as "no probes deployed" — they're different problems with different fixes.
- **Partial loads must surface.** When upstream is loaded but downstream isn't (or vice versa), the probe is degenerate — usually a manual edit broke one asset, OR the `_IO_MANAGER_ERROR` fallback path is masking a class-import problem. Both deserve operator attention; bundling them into "missing" would hide the asymmetry. Test `test_build_report_partially_loaded` enforces.
- **Unexpected probe-shaped assets are INFORMATIONAL, not blocking.** Stale files left over from a prior bundle still in `DAGTOOLS_PROBES_DIR` get listed in `unexpected_probe_asset_keys`, but `all_loaded` stays True if every expected probe is fully loaded. Cleaning them up is operator's call. Don't reverse this — failing the gate on stale files would force operators to wipe their probe dir every iteration.

### 4g0. Probe runner (`dag_tools.qual.probes`)
- **The probe state slot is SEPARATE from the runnable-rep state slot.** Probes live at `qualifications/<qual_id>/<side>/probes/state.json` + `<side>/probes/runs/<class_hash>/<run_id>.json`; runnable reps live at `<side>/state.json` + `<side>/runs/...`. A class can be both RUNNABLE (covered by a runnable rep) and SYNTHETIC_REQUIRED (covered by a probe) with neither path clobbering the other. `ProbeRepState` / `ProbeRepStatus` are distinct types from `RepState` / `RepStatus` so accidental cross-wiring fails at type-check time. Don't merge them.
- **The runner launches BOTH the upstream AND downstream asset in one run.** Selecting only the downstream does NOT auto-materialize the upstream — Dagster treats the upstream as a *loaded input* whose output must already exist in the IO manager, so a downstream-only launch dies with `DagsterExecutionLoadInputError`. Both must materialize in the same run: upstream writes via the real IO manager, downstream reads it back and asserts identity — that write→read is the whole point of the probe. (An earlier version launched downstream-only on the false assumption that `deps` co-materializes; live testing against `dagster dev` disproved it. Regression: `test_run_probes_side_launches_against_dag_tools_probes_location` asserts both keys.)
- **Hard-coded location name `dag-tools-probes`.** That's the contract with `dag_tools.probes_location.definitions`; if you ever need a configurable location, surface it through the qualification manifest's deployment config, not via a per-call override (the operator's deploy contract should be fixed across a qual_id).
- **Probe runs reuse the Q2 `RunRecord` schema.** So Q6 can diff probe runs the same way it diffs runnable-rep runs in the future. Don't fork the schema; if you need a probe-specific field, add it to `RunRecord` with a default so both paths stay forward-compatible.
- **PASSED is sacred, LAUNCHED reconciles via poll** — same invariants as Q2. Tests `test_run_probes_side_skips_passed_probes_on_re_invocation` + `test_run_probes_side_reconciles_launched_via_poll_not_relaunch` enforce them.

### 4g0a. Q6 synthetic coverage rollup (in `dag_tools.qual.verdict.verdict`)
- **`synthetic_classes_with_probe_coverage`** counts classes where probes PASSED on BOTH sides AND (when run records exist) the probe RunRecord diff cleanly. One-sided passes don't count. Removes the missing-coverage blocker for that class.
- **`synthetic_classes_red`** lists classes where the probe ran-and-FAILED on either side, OR both sides PASSED but the run records DIVERGED (a real regression signal that's exactly what Q6 exists to catch). Blocks GO **regardless** of `--accept-synthetic-coverage-missing` — that flag excuses missing coverage, NOT actively-failing or divergent probes. Don't add opt-outs. Tests `test_verdict_no_go_when_probe_failed_even_with_synthetic_accept` + `test_verdict_diverged_probes_blocks_go_even_with_passing_status` enforce this.
- **`synthetic_uncovered`** (classes neither green nor red — PENDING/LAUNCHED/not deployed) is what `--accept-synthetic-coverage-missing` excuses. When uncovered > 0 and the flag is False, that's the blocker.
- **Graceful degradation for missing records.** When probe state shows PASSED on both sides but the RunRecord can't be read (probe runs predate Q5e, or the record write was lost), the class still counts as covered. This is deliberate — the diff augments the status check; it doesn't replace it. Tests in `test_verdict.py` that synthesize probe state without records still pass.
- **`ClassVerdict.probe_diff`** carries the per-class probe RunRecord diff for SYNTHETIC_REQUIRED classes only. `UPGRADE_VERDICT.md` renders it in a dedicated "Failing SYNTHETIC_REQUIRED probes" section when the class lands in `synthetic_classes_red`.

### 4g2. Q2 IO round-trip probe (`dag_tools.qual.synthetic.roundtrip` + `dag_tools.qual.runs.roundtrip`)
- **Its state slot and types are separate again.** `RoundTripStatus` / `RoundTripState` are distinct from `RepState` and `ProbeRepState`, and live at `<side>/roundtrip/state.json` plus `<side>/roundtrip/runs/...` (keys owned by `layout.py`). Don't merge them. PASSED is sacred, LAUNCHED reconciles by poll, and only `DagsterRunNotFoundError` marks FAILED; any other poll error leaves it LAUNCHED. State is saved after every transition.
- **The probe writes nothing.** It returns `MaterializeResult`, so no value reaches an IO manager and nothing lands in the deployment's storage. It loads the upstream as an external `AssetSpec` bound to the real IO manager, so input loading is Dagster's own path. The import-failure fallback is `_ImportFailedIOManager`, whose `load_input` raises the import error; `InMemoryIOManager` would fail input loading with a misleading missing-key error first.
- **Freshness guard.** The pass skips (SKIPPED, re-evaluated next invocation) when the representative's latest materialization run id is not the Q2 run id: loading a newer output would compare the wrong data. It also skips when the representative's Q2 run did not PASS.
- **The partition is the one the Q2 run used**, from `RunRecord.partition_key`, falling back to the run's `dagster/partition` tag. Never recompute it with `last_partition_key`; it can have moved. If undeterminable, SKIPPED (uncovered), not FAILED.
- **Q6 parity exception, scoped to `dagtools/*`.** Metadata parity elsewhere is key-set only (4h). For the round-trip probe, shape parity compares the VALUES of `dagtools/loaded_type` and `dagtools/loaded_columns`, because a different loaded type or columns is exactly the regression the probe exists to catch. `dagtools/loaded_len` is informational and never gates. Don't extend value comparison beyond these two keys.
- **Buckets.** Covered: PASSED on both sides with equal type and columns. Red: PASSED on one side and FAILED on the other, or shape differs; blocks GO with no opt-out. Uncovered: anything else, including FAILED on both sides; excused by `--accept-roundtrip-missing`. Not applicable (dbt, no IO manager class): listed, never blocking. A RUNNABLE class with no round-trip coverage blocks GO by default; that is a behaviour change (CHANGELOG). The round-trip pass never changes `qual run`'s exit status.
- Regressions: `test_qual_roundtrip_runner.py`, `test_qual_roundtrip_generate.py`, `test_verdict_roundtrip.py`.

### 4g1. Synthetic probes (`dag_tools.qual.synthetic` + `dag_tools.probes_location`)
- **Generated source must always parse and the code location must always load.** The `dag-tools-probes` user-code location holds modules for every `SYNTHETIC_REQUIRED` class. One broken import there blocks the whole location. So the generator imports the real IO manager FQN inside a `try/except` with an `InMemoryIOManager` fallback and stamps the import error on `_IO_MANAGER_ERROR`; the probe asset raises that error at materialization, which is where operators can triage one probe at a time. Regression: `test_generated_source_parses_as_python` + `test_generated_source_has_inmemory_fallback_for_missing_io_manager`.
- **Each probe binds its IO manager under a class-unique resource key (`io_manager_<short>`).** `Definitions.merge` raises on conflicting resource keys; if every probe claimed bare `"io_manager"` the dag-tools-probes location would fail to assemble N probes. Regression: `test_each_probe_uses_class_unique_io_manager_resource_key` + `test_loaded_probes_merge_into_one_definitions_without_resource_collision`.
- **Probe IO manager constructor config comes from the manifest (`probes` block, `qual init --probe-config`), keyed by FQN, and env references stay references.** A no-arg construct only works for IO managers needing no config, so every other probe could never PASS and Q6 needed `--accept-synthetic-coverage-missing` forever. The primary key is the IO manager FQN, not `class_hash`, because class hashes change on every re-survey; `io_manager_config_by_class` is the deliberate narrow override and wins. A `{env: VAR}` value renders as `os.environ["VAR"]` and is **never resolved at generation time** — probe source is published to the registry and written under `~/.dagtools/quals/`, so resolving it would commit a credential to both; `ProbeModule.io_manager_config_keys` records kwarg names only. The construct stays inside the existing `try`/`except` (a wrong value degrades to `_IO_MANAGER_ERROR`, never a load failure), kwargs are sorted for byte-identical regeneration, and unrenderable values are rejected at manifest validation, never emitted. No config emits exactly the old no-arg line. Regressions: `test_env_reference_renders_os_environ_not_the_literal_value`, `test_the_construct_stays_inside_the_try_block`, `test_no_config_emits_the_no_arg_construct_unchanged`, `test_probe_manifest_records_config_key_names_never_values`, `test_class_hash_override_beats_the_fqn_entry`.
- **Probe resources travel key->FQN via `ClassMember`/`Representative`, and are bound OPT-IN per resource class FQN.** The class key discards resource keys on purpose (the hash must be stable across repos naming a resource differently) and must keep doing so; the keys ride on `ClassMember.resource_classes` -> `Representative.resource_classes` (class matrix schema 3). `probes.resource_config` (keyed by resource FQN, `{}` = no-arg construct) is the opt-in: a resource with no entry is NOT bound and is named in `notes`, because auto-binding could regress a probe that passes today (a resource connecting in `setup_for_execution` really connects) and a self-inflicted coverage regression is indistinguishable from a real Q6 finding. Do not "just bind everything". With no entries the source is byte-identical to pre-C3. Bound keys are suffixed `_<short>` or `Definitions.merge` collides; each resource has its own `try`/`except` feeding `_RESOURCE_ERRORS` and a failed resource is left out of `Definitions`, so one bad resource never takes the location down; the manifest records kwarg names only (`resource_config_keys`). The probe proves import/construct/availability on the context, not backend behaviour. Regressions: `test_synthetic_probe_resources.py` -- `test_no_resource_config_emits_source_identical_to_c1`, `test_two_probes_with_the_same_resource_key_do_not_collide_on_merge`, `test_a_resource_without_a_config_entry_is_not_bound_and_is_noted`, `test_a_failing_resource_does_not_reach_the_definitions_resources`, `test_env_reference_in_resource_config_never_renders_the_literal`, `test_each_resource_construct_is_in_its_own_try_block`.
- **Probes must NOT import `dag_tools.qual.*`.** They live in a separate code location with its own deploy cadence. If a probe imports the qual package, every `dag-tools` release becomes a probe deploy. Regression: `test_generate_probe_source_is_self_contained` — keep the probe surface to `dagster` + the IO manager FQN.
- **Manifest is written LAST.** `publish_bundle` writes every `<class_hash>.py` first and only then the `probe_manifest.json`. A reader observing the manifest is guaranteed every referenced source is present — same invariant as `latest.json`. If the manifest write moves earlier you've broken visibility.
- **The dag-tools-probes location soft-fails per probe.** `load_probes_from_dir` records every load failure on `ProbeLoadReport.failures` and continues — a syntax error or stale file in one `<class_hash>.py` MUST NOT block the whole location. Operators triage from the load log. Regression: `test_loader_soft_fails_a_malformed_probe`.
- **The dag-tools-probes location loads cleanly with no probes deployed.** `DAGTOOLS_PROBES_DIR` unset or pointing at a missing directory yields an empty `Definitions` — operators can deploy the location once and add bundles over time without re-deploying. Regression: `test_loader_returns_empty_report_when_env_unset`.
- **Run + Q6 coverage is wired, and so is the round trip for RUNNABLE classes (4g2).** `dagtools qual probes run --side <s>` launches every deployed probe (4g0), and Q6 counts a class as covered once its probes pass on both sides and their run records agree (4g0a). So `--accept-synthetic-coverage-missing` is needed only while some synthetic class is still uncovered, not whenever one exists. Don't paper over an uncovered class with a half-measure that fakes probe results.
- **v1 deferrals are notes, not silent gaps.** Partitions defs / partition mappings / dbt translators that the generator can't synthesize get captured in `ProbeModule.notes` and surfaced in the bundle — the operator sees them. Don't drop the notes when extending the generator; expand the synthesis instead.

### 4g. Preflight (`dag_tools.qual.preflight`)
- **All checks become entries in `PreflightReport.checks`, never raise.** A GraphQL failure during version lookup or workspace probing becomes a FAILED `CheckResult` with the error in `detail`. The whole point of preflight is the operator gets a report — crashing while reporting defeats it.
- **Baseline side has three checks; candidate side has four.** The fourth check (sampled baseline runs still render) only makes sense on the candidate — there are no priors to back-compat-check on the baseline side. Tests `test_baseline_preflight_does_not_sample_baseline_runs` and `test_candidate_preflight_samples_baseline_runs` enforce this.
- **`deployed_shas_match_pins` is PIN-DRIVEN so it cannot pass vacuously.** It iterates `manifest.inventory_pins`, not workspace locations: a pin with no matching stamped location FAILS, so a deployment with zero stamps fails instead of passing an empty `all(...)`. Locations without a repo stamp (notably `dag-tools-probes`) are informational (`unstamped_locations`) and never fail the check; stamped-but-unpinned repos are likewise informational. It reuses check 2's `code_locations` (no second workspace query) and runs on both sides. Dagster surfaces no git sha, so the stamp is an operator contract via `workspace.yaml` `additional_metadata` read from `displayMetadata`; key names come from `Deployment.repo_metadata_key` / `sha_metadata_key`, never hardcoded. Sha grammar is exact or a prefix of at least 7 chars, case-insensitive, and nothing else. Regressions: `test_preflight_fails_when_no_location_carries_a_stamp`, `test_an_unstamped_location_is_informational_not_a_failure`, `test_preflight_fails_when_deployed_sha_does_not_match_pin`, `test_preflight_rejects_a_prefix_shorter_than_seven_chars`, `test_sha_check_does_not_make_a_second_workspace_call`.
- **Every client GraphQL document is validated against the installed schema** in `test_graphql_query_schema_validation.py` (collected by reflection over `*_QUERY` / `*_MUTATION`), so the nonexistent-field bug class of 4f is now caught in CI.
- **Sampling is deterministic.** PASSED baseline run_ids are sorted lexicographically before slicing — re-runs probe the same runs, so a failure isn't a flake about which subset got picked. Don't change to random sampling without updating the contract.
- **Version comparison: exact, or wildcard `.x` suffix.** That's the entire grammar. `1.12.x` matches `1.12.0` through `1.12.999`. SemVer-style ranges, prereleases, and hashes are deliberately out of scope.

### 4f. Run execution (`dag_tools.qual.runs` + `dag_tools.qual.graphql`)
- **Save state after every transition.** The runner's resumability story depends on it. If a desktop dies between launch and persistence, the registry-mirrored state file is what makes the next invocation reconcile rather than re-launch. `test_run_side_state_is_mirrored_to_registry_after_each_transition` is the regression — if it fails, you've broken resumability.
- **PASSED is sacred.** A re-invocation MUST NOT re-launch a passed rep — that would burn duplicate compute and confuse Q6's diff (two run records for the same `(class_hash, asset_key)` on the same side). LAUNCHED reps reconcile via `client.get_run_status(run_id)`, not relaunch.
- **A failed poll is not a failed run.** `poll_to_completion` raising (timeout, transport error, a non-terminal event-log read) says nothing about the run, which may still be executing, so the rep stays LAUNCHED with the error noted and the next invocation reconciles it. Marking it FAILED, as the runner once did, let the next pass launch a second, concurrent run of the same representative. The one permanent case is `DagsterRunNotFoundError` (the `RunNotFoundError` union member, matched by typename): that run will never finish, so it is FAILED and relaunched. Q2, the probe runner and `qual stage` all follow this rule. A probe left LAUNCHED counts as uncovered in Q6, not red, because nothing failed. Regressions: `test_a_poll_timeout_leaves_the_rep_launched_and_is_never_relaunched`, `test_a_run_that_no_longer_exists_fails_so_the_next_pass_relaunches`, `test_a_probe_poll_timeout_stays_launched_and_reconciles`, `test_an_unknown_run_id_raises_the_permanent_not_found_error`.
- **GraphQL drift is expected.** The client uses public fields only and falls back gracefully on unknown event subtypes (records them as raw dicts with what we could decode). If a Dagster version surfaces a new event subtype that matters for run records, extend the parser in `build_run_record` — don't add internal-attribute access.
- **Never select a GraphQL field that doesn't exist on the target type.** A nonexistent field in an inline fragment (e.g. `... on InvalidStepError { message }` — `InvalidStepError` only has `invalidStepKey`) 400s the ENTIRE request, not just that field — silently breaking every launch. When editing `LAUNCH_MUTATION`/`STATUS_QUERY`/`LOGS_QUERY`, introspect the live schema (`__type(name:...){ possibleTypes { name fields { name } } }`) and select only present fields. Regression: `test_launch_mutation_does_not_select_message_on_fieldless_error_types`. This class of bug is invisible to unit tests that mock the transport — only live testing or schema introspection catches it.
- **The launch location comes from the manifest, never a hardcoded default.** `run_side` threads `manifest.deployment.location_name` / `job_name` into `launch_representative`. The launcher's `"default"` fallback only exists for the degenerate case; real deployments name their location after the user-deployment / gRPC server, and `dagtools qual init --location-name` is how the operator sets it. Regression: `test_run_side_threads_manifest_location_and_job_into_launch`.
- **Launch the representative ALONE; widen only when the deployment refuses.** A representative is one asset per equivalence class, so op-mates are compute the qualification never reads. The launcher used to sweep in every asset sharing the representative's op *pre-emptively*, to get ahead of a non-subsettable `multi_asset` — but Dagster refuses a partial selection only when `can_subset=False` (`asset_job.py`'s `DagsterInvalidSubsetError` is in the `else` branch; a subsettable definition takes `asset.subset_for(...)`). `@dbt_assets` IS subsettable and translates a one-key selection into a one-model `--select`, so the sweep was pure cost: a consumer's 22-model dbt project built all 22 models on every representative launch, and the dragged-in models mostly FAILED because their own upstreams were never selected. Subsettability cannot be introspected first — `AssetNode` exposes no `canSubset` (checked against dagster-graphql 1.13.1) — so `plan_asset_selection` selects precisely and `launch_representative` retries through `expand_to_op_siblings` on, and only on, `DagsterSubsetNotSupportedError` (the `InvalidSubsetError` union member, matched by typename, never by dagster's message wording). Regressions: `test_a_subsettable_dbt_op_does_not_drag_in_the_whole_project`, `test_the_whole_project_is_not_launched_through_the_real_entrypoint`, `test_a_refused_partial_selection_is_retried_with_the_op_mates`, `test_other_launch_failures_are_not_retried`.
- **Q2 does not materialize upstreams; `qual stage` does (next bullets).** Dagster treats an unmaterialized upstream as a *loaded input* whose output must already exist in the IO manager, so a representative whose upstreams are not external needs data staged for it. The supported mechanisms are now documented in `docs/RECIPE.md` ("Staging data for Q2"): dbt `--empty` (component `cli_args` or `DBT_EMPTY`) and, for everything else, operator-staged data pointed at via `staging_overrides`; generated seeder assets remain unbuilt. Do not paper over it by expanding the selection to include upstreams; that silently turns a one-asset comparison into a whole-subgraph build and reintroduces the bug above.
- **`manifest.staging_overrides` is a POINTER, and it must be resolved before any launch.** The field holds an `s3://...` (or local path) URI naming a run config document, which the manifest docstring always said Phase 2 "pulls as run_config". Nothing pulled it: both launchers wrote the pointer *string* into run config under a fabricated `__staging_overrides__` key, and Dagster accepts only `ops` / `resources` / `execution` / `loggers` at the top level — so every launch with `--staging-overrides` set died at submission with `DagsterInvalidConfigError`, and the feature had never worked at all. The unit tests missed it because they asserted on the dict the launcher built rather than on whether Dagster would accept it; assert top-level keys are a subset of `RUN_CONFIG_TOP_LEVEL_KEYS`. Resolution lives in `dag_tools.qual.runs.staging` and happens **once per side** in each runner, next to `get_asset_launch_info` and for the same reason (a whole-deployment fact, not a per-rep one); the launchers stay pure and do no IO. Unlike `launch_info`, a resolution failure does **not** degrade to empty — launching against un-overridden resources would bank run records that look like a qualification but describe the wrong deployment — and a launcher handed a declared-but-unresolved pointer raises `StagingOverridesNotResolved` rather than launching. The merge is **recursive** (`explicit` wins at the leaf): run config nests as `resources -> <key> -> config`, so a shallow merge of a per-rep `resources` block would silently drop every staging resource the operator did not restate. Regressions: `test_qual_staging_overrides.py` — `test_the_pointer_itself_never_reaches_run_config`, `test_launched_run_config_has_only_keys_dagster_accepts`, `test_an_unresolved_pointer_raises_instead_of_launching`, `test_merge_is_recursive_so_a_per_rep_block_does_not_drop_siblings`, plus the probe-launcher pair that carried the identical bug.
- **The Q2 IO round-trip probe is built (4g2).** It launches a real probe through `dag-tools-probes`; do not replace it with a half-measure that fakes a result.
- **`qual stage` materializes the upstreams Q2 reads, in a slot of its own, and Q2 does not change.** (`dag_tools.qual.stage`.) State and records live at `<side>/stage/` with types (`StageState`, `StageRecord`) distinct from the rep and probe slots; `StageRecord` is not a `RunRecord`, so Q6's diff has nothing to key it on. `staging_overrides` are mandatory: a declared pointer that is unresolved raises `StagingOverridesNotResolved`, and an empty `launch_info` refuses to launch (unlike Q2), because staged outputs landing in the wrong place would bank a qualification of the wrong deployment. Q2's selection stays the representative alone; `qual run` only warns when `required` reps exist and stage has not passed for the current selection hash. Q6 reads the stage state to record `stage_by_side` and never compares it: it must not reach `status` or `blocking_issues`. One run per partition group (a run cannot mix partition definitions), launched in dependency order, a failed group skipping only its dependents, cross-group cycle keys reported not launched. Staging is per side, so re-run it after the candidate upgrade. Regressions: `test_qual_stage.py` -- `test_stage_run_tags_carry_purpose_and_no_class_hash`, `test_unresolved_staging_pointer_raises_instead_of_launching`, `test_empty_launch_info_refuses_to_launch`, `test_q2_selection_is_unchanged_by_stage`, `test_q6_status_is_identical_with_and_without_stage_artifacts`, `test_stage_status_never_reaches_blocking_issues`, `test_two_partition_definitions_launch_as_two_runs_in_dependency_order`, `test_a_failed_group_skips_only_the_groups_that_depend_on_it`, `test_passed_is_sacred_for_the_same_selection_hash`, `test_changed_selection_hash_launches_again`.

### 4e. Equivalence-class matrix (`dag_tools.qual.classes`)
- **Q1 reads the manifest, not the registry.** `build_class_matrix` walks `manifest.inventory_pins[]` and fetches each pinned SHA's `assets.json` + `dbt_projects.json`. It never calls `read_latest_pointer`. If you write a new Q-phase, follow the same pattern — that's how the qualification stays reproducible.
- **The class hash is deterministic.** Identical `ClassKeyComponents` → identical 12-char SHA-256 prefix. Tests in `test_classes_key.py` enforce this. Don't introduce nondeterministic ordering or transient state into the components.
- **Custom dbt translators always form their own class.** The detection joins `assets.json` (looking for `dagster_dbt` in `integration_libs` or `compute_kind == "dbt"`) with `dbt_projects.json` (looking for `is_custom_translator: true`). Conservative: any custom translator in the repo gets attached to every dbt asset's key. That can over-segregate but never under-segregates.
- **Runnability is tag-driven**, not FQN-inferred. The contract: `synthetic_required: "true"` / `observe_only: "true"`. Adding inference rules (e.g. "Snowflake is always synthetic") is a backwards-compatibility hazard — different orgs have different staging realities. If you want to add such a rule, gate it behind a manifest knob.
- **Staging need is reported, never gated, and `None != []`.** `AssetRecord.upstream_asset_keys` (inventory schema v3) has three states: `None` = the survey predates the field or the lookup failed (UNKNOWN), `[]` = genuinely no upstreams, non-empty = the declared deps. A `None` must NEVER classify as `NONE_NEEDED` — an un-resurveyed inventory reporting "nothing needs staging" is the same vacuous-pass bug the preflight sha check avoids. `build_executability_index` spans ALL pinned repos and resolves a key as executable if ANY pinned repo computes it (REQUIRED), because if anything in the fleet computes that key its output will not exist when Q2 launches one asset alone; this over-reports rather than under-reports, matching the class key's stance. `REQUIRED` outranks `UNKNOWN`. `ClassMatrix.launchable_now_count` (`RUNNABLE` and `NONE_NEEDED`) is the real answer to "how much can Q2 actually run today"; `NONE_NEEDED` means no staged *Dagster* output is needed, not that the external source exists. This bullet only *reports*: `Runnability` and every launch path are untouched. Closing the gap is the operator's job through the documented mechanisms (`docs/RECIPE.md`, "Staging data for Q2"); generated seeder assets remain unbuilt. Regressions: `test_qual_staging_need.py` — `test_pre_v3_inventory_classifies_unknown_not_none_needed`, `test_upstream_executable_in_any_repo_means_staging_required`, `test_required_wins_over_unknown_when_both_apply`, `test_launchable_now_counts_only_runnable_and_unstaged`, `test_staging_need_does_not_change_runnability`, `test_pick_representatives_without_index_yields_unknown`.

### 4d. Qualification manifest (`dag_tools.qual.qualify`)
- **The manifest is the contract for everything in Phase 2.** Q1–Q6 read it; none of them re-read the registry's `latest.json` directly. If you write a Q-phase that calls `read_latest_pointer` instead of the manifest's `inventory_pins[]`, you've broken qualification reproducibility — a mid-qualification CI publish would silently change the qualification target.
- **One qual_id per qualification, immutable.** `create_qualification` writes via the immutable registry put. Re-running with the same id raises `ImmutableKeyExists`. `--allow-overwrite` exists for the deliberate "redo this qualification" path; don't silently fall back to it.
- **`co_upgrade_risks` exists to surface hidden dbt-core / warehouse / dbt-adapter bumps inside a Dagster upgrade.** The diff explicitly filters the Dagster family (anything matching `dagster*`) because those are the explicit upgrade target. Tests in `test_qualify_risks.py` cover the matrix; extending the diff means extending the tests.
- **Recipe-aliased YAML.** `CoUpgradeRisk` uses `from`/`to` (not `from_version`/`to_version`) on disk, matching the recipe sample in `docs/RECIPE.md`. Always serialize with `by_alias=True`.

### 4c. Survey (`dag_tools.qual.survey`)
- **The load-gate invariant is non-negotiable.** `run_survey` refuses to write anything to the registry when any code location fails to load. The recipe spelled this out: "the registry never contains an inventory for code that doesn't load." This is the contract that makes every downstream qualification phase safe; without it, qualification operators would burn cycles diagnosing inventory drift caused by broken code. The test `test_run_survey_refuses_to_publish_when_load_fails` is the regression — if you change the publisher's control flow and that test fails, the failure is the system warning you off.
- **Capture every warning emitted during load.** Use the `_capture_warnings` context manager (it sets `simplefilter("always")` — equivalent to `python -W all`) around every `importlib` call. Deprecations and experimental-API warnings are part of `load_validation.json`; that's how operators see Dagster drifting across the fleet without manual scraping.
- **Per-item soft-failure**, same discipline as the inventory extractor. One malformed sensor must never abort the whole introspection pass.
- **One pydantic schema per artifact**, each with its own `SCHEMA_VERSION_*` constant. Same additive-only evolution rules as `AssetRecord`. When adding fields, bump the relevant `SCHEMA_VERSION_*` in the same commit; readers tolerate unknown fields.

### 4b. Qualification Registry (`dag_tools.qual.registry`)
- **The layout module owns every S3 key.** `dag_tools/qual/registry/layout.py` is the only place where key strings are constructed. Writers and readers compose paths via helpers like `inventory_artifact_key(repo, sha, filename)` and `latest_pointer_key(repo)`. **Never** literal-string an S3 key anywhere else in the codebase.
- **Immutability is enforced at the storage layer.** Every per-build artifact uses `S3Storage.put_immutable`, which HEAD-then-PUTs and raises `ImmutableKeyExists` on collision. Only `latest.json` (and the equivalent qualification pointers) use `put_mutable`.
- **`latest.json` is written LAST.** `InventoryRegistry.publish_build` writes all immutable artifacts first, then updates the mutable pointer. **Do not reorder** — this invariant is what makes partial publishes invisible to readers. The test `test_pointer_not_updated_when_artifact_write_fails` enforces it; if you change the publish ordering, that test will fail and that failure is the system telling you to stop.
- **Machine-readable JSON is the default CLI output**, per the recipe rule "Every command is idempotent and emits machine-readable JSON". Every `dagtools` sub-command must accept `--format` defaulting to `json`, with `table` available for human consumption.

### 4a. Shared Inventory Contract (`dag_tools.inventory`)
- The `AssetRecord` pydantic schema in `dag_tools/inventory/schema.py` is the **cross-process contract** between the runtime Domain Broker (long-lived pods, last quarter's release) and the CI Dagster qualification survey (every commit, today's release). They will read each other's records across versions.
- **Evolution rules**: additive-only. Never rename or remove fields. Only add new `Optional[...]` fields with defaults, and bump `SCHEMA_VERSION` by 1 in the same commit. Readers tolerate unknown fields via `extra="ignore"`. If you truly need a breaking change, it's a major library version and requires coordinated rollout — talk to the runtime mesh team first.
- **IO manager classification**: extend `dag_tools/inventory/classifier.py::FAMILY_REGISTRY` with the FQN of any new IO manager. MRO walking catches custom subclasses of registered ancestors. The substring fallback is a logged-at-WARNING last resort whose presence in the logs is a signal to add a registry entry.
- **Soft-failure discipline**: the extractor must never abort because one asset is malformed. Wrap every field access in per-field exception handling; record `None` and log WARNING. The whole point of the schema being mostly-optional is to make this safe.

### 5. Normalized Configuration Design
- **Dagster Configuration First**: All new components and resources MUST use the Dagster configuration framework (`Config`, `ConfigurableResource`, or `dagster.components` attributes).
- **Wrap & Standardize**: Do not expose raw, pass-through configurations for underlying tools (like `dlt` or `dbt`) directly if they deviate from Dagster's standard practices. Instead, define a Dagster-centric configuration schema that wraps and translates to the native tool's requirements.
- **Component Translation**: The component's `build_defs()` or the resource's initialization logic is responsible for mapping these standardized Dagster inputs into the specific format required by the underlying engine.

### 6. Backwards Compatibility
- Since other repositories (like `pub-tools`) depend on `dag-tools`, **DO NOT** make breaking changes to function signatures or export names without explicit approval from the user. 
- If adding a new feature to an existing shared component, make the new parameters optional with sensible defaults.

### 8. Release Images (`.github/workflows/build-containers.yml`)
- **A commit is built once; a release tag RENAMES that build.** The `build` job is gated `if: github.ref_type != 'tag'` and emits no `type=semver` pattern; the `retag` job is gated `if: github.ref_type == 'tag'` and GETs the `:sha-<short>` manifest, then PUTs **its own bytes** under `X.Y.Z` (plus `X.Y` only for a plain three-number version). Before this, the tag push ran the build a second time, so one commit had two digests and a deployment pinning the release pinned bytes no commit tag named — measured on `v0.11.0` vs `sha-4924235`: different config blob and most layer blobs different. Nothing in this build is reproducible (every run resolves dependencies fresh — `s3fs` came out `2026.9.0` against `0.4.2` three commits earlier — and layer metadata carries build time), so a second build of one commit can never be the same image.
- **Do NOT use `docker buildx imagetools create` to do the rename.** It assembles a fresh index from its sources, and these images carry buildx attestation manifests, so digest preservation is not guaranteed — which is the one thing the job exists to provide. The manifest bytes go across verbatim, and the `Accept` header must list all four manifest media types or the registry may answer with a *converted* manifest whose digest differs.
- **`:latest` is a MASTER pointer and a tag must not move it.** Only the branch build pushes it. docker/metadata-action counts a tag ref as the default branch (`is_default_branch` is true for a tag), which is how a mistaken tag briefly published `:latest` from the wrong tree.
- **A tag on a commit master never built fails loudly.** The retag polls for `:sha-<short>` (60 × 20s, covering the normal merge→tag gap) and then errors rather than falling back to a build. The source tag is spelled `sha-${GITHUB_SHA:0:7}` to match metadata-action's `type=sha`; if that action's length ever changes, this fails instead of silently rebuilding.
- Regressions: `test_image_release_retag.py` — `test_a_tag_ref_does_not_build`, `test_the_build_job_emits_no_semver_tag_pattern`, `test_the_retag_job_builds_nothing`, `test_the_release_does_not_move_latest`, `test_the_release_name_is_not_minted_by_imagetools_create`, `test_the_retag_verifies_the_release_resolves_to_the_source_digest`, `test_a_missing_commit_build_fails_instead_of_building`, `test_every_built_service_is_retagged`.
